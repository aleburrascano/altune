Independent workflows, each scoped to a path or schedule.

**test-backend.yml** — the baseline gate. Triggers on PRs and pushes to `main` touching `services/go-api/**`. Runs `go vet ./...`, then depguard via `golangci/golangci-lint-action` (pinned v2.12.2 — v2.3.0's binary was built with Go 1.24 and refused to lint once `go.mod` moved to `go 1.25.0`, failing every run at this step until the bump; rules in `services/go-api/.golangci.yml` — domain-purity and shared-never-imports-features, per the structure-audit F1 enforcement), then `go test -race -count=1 -coverprofile=coverage.out ./...` with `CGO_ENABLED=1` on an ubuntu-latest runner (the race detector needs cgo, which the dev box — Windows, no C toolchain — can't provide locally; this is where data races in concurrent telemetry code, e.g. the log ring, event tap, provider store, scheduler counters, alert monitor, are actually caught). A final **coverage ratchet** step reads that profile and fails the job if total statement coverage drops below a hardcoded `MIN` (65 when the step was added, the baseline measured then; **62 since 2026-07-31**). The floor is a regression guard, not a target — raise it after hardening a module, never lower it to make CI green.

That principle has exactly one exception on record, and it is worth reading as a lesson about gates rather than about coverage. The floor was breached for at least eight consecutive runs (62.1% → 62.2% → 62.4%) and blocked nothing, because this workflow and `deploy-backend.yml` fired on the same push and ran in **parallel** — the deploy never waited for the verdict, so a red ratchet was invisible. `cb26d1c` (2026-07-30) made the deploy `needs: test`, and the very next backend push was the first thing the floor had ever actually stopped. A gate that has been failing unobserved does not announce itself when it starts working; it presents as the *next* unrelated change appearing to break the build, and the first instinct is to blame that change. Here it was measurably innocent — coverage read 62.7% locally at the blocked commit, at its parent, and at the last deployed commit alike. Wiring a gate to be load-bearing therefore has a cost nobody budgets for: whatever debt accumulated while it was ornamental lands on whoever pushes next. Lowering the floor to 62 was the deliberate, recorded choice to pay that later rather than then; the ratchet back to 65 is owed and tracked in [programme](../testing/programme.md)'s Outstanding section, along with where the missing points live. Coverage alone is a weak signal, so the number is not the quality gate: the `qa-slice` skill gates on whether mutating a covered line turns the suite red. The mobile side has an equivalent ratchet in `apps/mobile/jest.config.js`, now **per-glob** rather than one global average — a single blended number let an uncovered reducer hide behind well-covered UI, which is how `shared/events` reached a 0% mutation kill rate with the global floor satisfied. It is enforced by `test-mobile.yml`, added 2026-07-30; until then nothing in CI executed the mobile suite at all.

**test-mobile.yml** — the mobile counterpart to `test-backend.yml`, and blocking. Triggers on PRs and pushes to `main` touching `apps/mobile/**`. Generates the expo-router typed-routes declaration first (`npx expo customize tsconfig.json`) — `app.json` sets `experiments.typedRoutes`, so `.expo/types/router.d.ts` is *generated*, `tsconfig.json` includes it and `.gitignore` excludes it; a dev machine has it from the last `expo start` and a fresh CI checkout does not, which made CI typecheck against a fallback where `useSegments()` is a `[string]` 1-tuple. The very first real run of this workflow failed on exactly that (`FeaturingScreen`'s `segments[1]`), clean locally and broken in CI. Then runs `tsc --noEmit`; `eslint` (where the feature-isolation zones are enforced — the analogue of the backend's depguard rules); **fallow** `dead-code` and `dupes` at zero tolerance, plus a complexity **ratchet**; `jest --coverage --ci` against the per-glob floors; and a **react-doctor** gate. Five kinds of check, three different gating shapes — zero-tolerance where the count is already zero, a ratchet where it is not, and a floor for coverage.

The two static-analysis gates were added on 2026-07-30, when both tools turned out to be installed and effectively unwired: `fallow` was a devDependency that no script and no workflow ever invoked, and react-doctor ran only advisory. Each needed a correction before it could gate anything.

*fallow* (`.fallowrc.json`) covers unused code, unused dependencies, circular imports, architecture boundaries and complexity health. Two problems had to be fixed first. Its `boundaries.rules` permitted `feature-detail -> feature-playback`, three `feature-* -> feature-auth` edges and even `shared -> feature-auth` — all forbidden by `apps/mobile/CLAUDE.md` and all blocked by eslint, so fallow was quietly encoding a *more permissive* architecture than the one enforced. Tightening the zones produced zero new violations, proving they were dead permissions. And **fallow's exit code ignores rule severity**: `fallow dead-code` exits 0 even with an `error`-severity finding, verified by flipping `unused-dependencies` to `error` and observing 0. `--fail-on-issues` is the flag that actually gates; a bare `run: fallow dead-code` step would have been decorative. `dead-code` and `dupes` both report clean, so they are zero-tolerance. `health` reports 137 findings — mostly "split this high-impact file" and "these complex functions have no test-coverage path", i.e. prioritisation advice rather than defects — so it is a **ratchet** — currently `continue-on-error`, because the first CI run scored 145 against the 137 measured locally. fallow's health scoring weights git churn and `actions/checkout` clones at depth 1, so the workflow now uses `fetch-depth: 0` to make the analysis the same kind in both places; the ceiling still has to be re-measured from a green CI run before the step can block. A ratchet whose number depends on the environment gates nothing honestly. Parsed from **stderr** (fallow writes its summary there, and the step fails rather than defaulting to zero if the parse comes back empty).

*react-doctor* had 108 findings including 2 errors, both `query-destructure-result`: `useDiscoverSearch` returned `{ ...infinite, data }`, and spreading a TanStack Query result touches every getter so the component re-renders on any field changing. Fixing both took it to 106 findings, 0 errors, exit 0 — which is what made it gateable at all. The gate asserts `errorCount == 0` with a warning ceiling of 106, and runs the **pinned** devDependency rather than `npx react-doctor@latest`: a gate must not change behaviour because upstream shipped a new rule. `react-doctor.yml` keeps the action for its sticky per-PR delta comment, which *is* allowed to track latest. It checks out the **whole repo**, not just `apps/mobile`: the cross-surface contract test derives the backend's published event names from `services/go-api` source at test time, so the Go tree must be on disk.

**mutation-mobile.yml** — cron `20 3 * * *` plus manual dispatch, running Stryker (`npm run mutate`, config in `apps/mobile/stryker.config.json`) over the slices listed in `mutate`. This is the gate that answers what coverage cannot: whether the tests *constrain* the code or merely execute it. Scheduled rather than per-PR because a full run mutates hundreds of variants — `test-mobile.yml` is the fast gate, this is the slow truth. The `break` threshold is a ratchet on the same terms as the coverage floors: raise it when a slice is hardened, never lower it to go green. The report is uploaded as an artifact even when the job fails, because the surviving-mutant list is the actionable output and a red run is exactly when you want to read it. Stryker's sandbox lives at the repo root (`../../.stryker-tmp`) deliberately — inside `apps/mobile` it sits under jest's `rootDir` and jest collects the sandbox's own copies of every test file, silently doubling the suite.

**react-doctor.yml** — the only mobile-scoped gate, and advisory (`blocking: warning`). Triggers on PRs and pushes to `main` touching `apps/mobile/**`, running `millionco/react-doctor@v2` with `directory: apps/mobile` against the rule overrides in `apps/mobile/doctor.config.ts`. It spent its whole life until 2026-07-25 at `apps/mobile/.github/workflows/react-doctor.yml`, where GitHub never looked — Actions reads workflows only from the repository-root `.github/workflows/`, so a nested copy is an inert file that reads like live CI. It has therefore never gated anything, which is why it was promoted as advisory rather than blocking: its first real run is expected to surface a backlog.

**discovery-eval-gate.yml** — a narrower quality gate layered on top, scoped only to PRs touching ranking-path files: `service/rank*.go`, `merge*.go`, `diversity*.go`, `pipeline*.go`, `behavioral_signals*.go`, `service/eval/**`, `cmd/discoveryeval/**`. It checks the harness compiles (`go build ./cmd/discoveryeval`) and runs the deterministic rank/merge/eval/behavioral-corpus/replay unit tests (`go test ./internal/discovery/service/... ./internal/discovery/service/eval/...`). It deliberately does NOT run the full positional eval (`cmd/discoveryeval -mode eval`, needs live providers + DB/Redis, see [eval-harness](../backend/discovery/eval-harness.md)) — that stays nightly/on-demand. Exists because a plausible ranking improvement once turned out to be a same-sample regression (per `discovery-eval-harness-program` project memory) — this gate stops a ranking diff merging without deterministic checks passing.

**deploy-backend.yml** — triggers on push to `main` touching `services/go-api/**`, or manual dispatch. A `test` job **calls `test-backend.yml` as a reusable workflow** and `deploy` declares `needs: test`. Until 2026-07-30 the two workflows fired on the same push and ran in parallel, so a deploy could reach production while its own tests were still running — or after they had already failed. A called workflow runs against the caller's ref, so the gate tests exactly the commit being shipped rather than whatever else happened to be green. The cost is that a push to main runs the backend checks twice, once standalone and once as the gate; that is deliberate, so `test-backend.yml` stays the independent record that main is green even if this workflow is edited or fails on infrastructure. No separate call to `discovery-eval-gate.yml` is needed — its `go build ./cmd/discoveryeval` and `go test ./internal/discovery/service/...` are strict subsets of test-backend's `go vet ./...` and `go test -race ./...`. `concurrency.group: deploy-backend` with `cancel-in-progress: false` serializes deploys. Steps: warns (doesn't block) if the push touched `services/go-api/migrations/` — schema migrations are applied manually via psql, by design, never by the pipeline; verifies `DEPLOY_HOST`/`DEPLOY_USER`/`DEPLOY_SSH_KEY` secrets are present; SSHes in (`appleboy/ssh-action`) and runs `git pull --ff-only origin main` + `bash deploy/blue-green.sh` on the VM. The script owns the whole swap — build the idle colour, health-gate it before any traffic moves, flip the Caddy upstream, verify publicly, roll back if that fails — so the workflow no longer polls `/health` itself (the gate is now inside the deploy, where it can still act on the result) and no longer hand-clears stale containers (recreates happen on an idle colour, so the name conflict that cleanup existed for cannot arise). On any failure the run prints the `deploy/rollback.sh` command. See [production-deployment](production-deployment.md) for the topology and the blue-green mechanics.

**release-ios.yml** — gated since 2026-07-30 by a `verify` job that **calls `test-mobile.yml`**, with `build` declaring `needs: verify`. test-mobile triggers on pull requests and pushes to `main`, so a tag push matched nothing and every `.ipa` published here shipped with no typecheck, no lint and no tests — the one place code reaches real devices was the least gated in the repo. Verification runs on a cheap ubuntu runner before the macOS build starts. Otherwise: triggers on a `v*` tag push or manual dispatch with a version input. Builds an **unsigned** iOS `.ipa` on macos-15 (Expo prebuild → CocoaPods → `xcodebuild archive` with `CODE_SIGNING_ALLOWED=NO`) for sideloading via AltStore/SideStore (which re-sign on-device with the user's own Apple ID — no Apple Developer account needed). Publishes a GitHub Release with the `.ipa`, then a second job updates the AltStore manifest (`apps.json`) on a dedicated, unprotected `altstore` branch via `scripts/update-altstore-source.mjs` so existing installs see the new version.

**uptime-check.yml** — cron `*/5 * * * *` (GitHub's minimum granularity) plus manual dispatch. Curls `UPTIME_HEALTH_URL` (a repo Environment secret named "uptime") and, on non-200 or unreachable, pushes an ntfy alert (`UPTIME_NTFY_URL`, optional). Exists because the in-process alert monitor (see [alerting](../backend/admin/alerting.md)) dies with the box and can't report total outage — this runs off-box on GitHub's infrastructure, $0 cost, storing no topology (only the health URL/ntfy URL as secrets).

**Gotcha**: only `test-backend.yml`, `test-mobile.yml` and `discovery-eval-gate.yml` gate PRs. `deploy-backend.yml` fires on push to `main` (post-merge), so a merged PR auto-deploys to production — the only manual step left is applying migrations. Both shipping paths now gate themselves by calling the matching test workflow (`deploy-backend` → `test-backend`, `release-ios` → `test-mobile`), so the pattern to follow for any future pipeline is `uses: ./.github/workflows/<gate>.yml` plus `needs:`, never a parallel workflow on the same trigger. `react-doctor.yml` remains advisory and is the one gate still not blocking; promoting it needs a triage pass first, since it has never gated anything and is expected to surface a backlog.

## Acquisition selection gate (2026-07-26)

`test-backend.yml` gained a step after `go test -race`: `go run ./cmd/acquisitioneval -baseline ./cmd/acquisitioneval/baselines.json`. It runs acquisition's real `CoreSteps` pipeline in-process against committed goldens and exits non-zero if overall or per-failure-class accuracy drops more than 1% below the committed baseline. Provider-free and offline — no network, no database — so unlike `discovery-eval-nightly.yml` it can gate every PR rather than run on a schedule. Re-baselining is explicit (`-update-baselines`), and the baseline is a floor, never lowered to make CI green. A duplicate assertion lives in the Go suite (`TestEmbeddedSuiteMatchesCommittedBaseline`) so the same regression fails locally before it reaches CI.
