**Topology.** Postgres is external — Supabase, not containerized here, reached through the **session-mode pooler on port 5432** (this matters: see the advisory lock below). Redis is self-hosted on the VM, containerized, not persisted (`--save "" --appendonly no`), capped at `--maxmemory 256mb --maxmemory-policy allkeys-lru`, and NOT published to the host — reachable only over the compose network (`REDIS_URL=redis://redis:6379/0` in `.env.production`). Caddy (`caddy:2-alpine`) is the reverse proxy/TLS terminator, exposing 80/443, auto-provisioning Let's Encrypt certs. The API containers build from `deploy/Dockerfile` against the module root as context, read secrets from `.env.production` (`env_file`, gitignored — the repo is public, and the file stays at the module root as untracked VM state, referenced as `../.env.production`), and hardcode several non-secret values in the compose `environment:` block: `OPERATOR_USER_ID` (Mission Control operator account, see [console-surfaces](../backend/admin/console-surfaces.md) — not secret, `/admin` still requires that account's Supabase JWT), `EVAL_METER_ENABLED=true`, and `SUPABASE_ANON_KEY` (public client key). They depend on Redis being healthy, mount a cookies file (`/home/ubuntu/altune/cookies.txt:/data/cookies.txt`, for yt-dlp auth, see [pipeline](../backend/acquisition/pipeline.md)) and a `tmpfs` `/tmp:size=1G`. Caddy's cert state persists in named volumes `caddy-data`/`caddy-config`.

## Blue-green (2026-07-25)

**What it replaced, and why.** The old deploy ran `docker compose up --build -d` against a single `altune-go-api` container. The build happened while the old container still served, so the outage was only the recreate — but it was a real outage on every deploy, and the recreate was fragile enough that the workflow carried a hand-written cleanup for containers left behind by an interrupted swap (compose renames the old container to `<id>_altune-go-api` before replacing it; an interrupted swap left that behind and the next recreate died on a name conflict). Worse, the health check ran *after* the swap and, on failure, only turned the CI run red — production stayed broken until someone SSHed in. **There was no rollback path at all.** That was the actual hole; the seconds of downtime were the smaller half.

**The two colours.** `deploy/compose.prod.yml` defines `go-api-blue` and `go-api-green` off a shared YAML anchor, with distinct container names (`altune-go-api-blue` / `-green`) and distinct image tags (`altune-go-api:blue` / `:green`). Distinct tags are what make rollback instant: building green never overwrites the image blue is running, so the previous version is always still on disk. Neither publishes a host port — Caddy is the only ingress, and two containers cannot both bind 8000 anyway.

**How traffic moves.** `deploy/Caddyfile` is a one-liner that `import`s `/etc/caddy/upstream.conf`; that file holds nothing but `reverse_proxy altune-go-api-<colour>:8000` and is the single source of truth for which colour is live. `deploy/blue-green.sh` rewrites it and runs `caddy reload`, which is graceful — in-flight requests finish on the old upstream. **`deploy/caddy/upstream.conf` is deliberately gitignored**: the deploy does `git pull --ff-only`, and a tracked file that the VM rewrites every deploy would make the pull fail on local modifications. The script seeds it to blue when absent.

**The sequence** (`deploy/blue-green.sh`, helpers in `deploy/lib.sh`): read the active colour → build the idle one → start it → poll its `/health` *from inside the compose network* (`docker compose exec caddy wget …`, up to `HEALTH_TIMEOUT`, default 180s) → flip the upstream and reload → verify the **public** URL → drain `DRAIN_SECONDS` (default 20) → stop the old colour. Two distinct failure paths, and the distinction is the point:

- **Candidate never goes healthy** → its logs are dumped, it is stopped, the script exits 1. Caddy is never reloaded; the upstream file is never rewritten. The live colour did not notice a deploy happened.
- **Public check fails after the flip** → the upstream is rewritten back to the previous colour, Caddy is reloaded again, the candidate is stopped, exit 1. This is why the old colour is stopped only *after* the public verify: it is the rollback target, and stopping it first would leave nothing to fall back to.

The old colour is stopped, never removed, so `deploy/rollback.sh` can bring it straight back (start → health-gate → flip → verify) without a rebuild. The workflow prints that command on any failure; run it from `services/go-api` on the VM, either as `./deploy/rollback.sh` (the scripts are committed executable) or `bash deploy/rollback.sh`. It health-gates the returning colour exactly as a deploy does, so a rollback to a version that no longer boots refuses to move traffic rather than trading one outage for another.

**Why the health check runs through the Caddy container** rather than from the runner: the candidate has no published port and no DNS name outside the compose network, and checking it from GitHub would only prove Caddy answers — which it does, on the *old* colour. The gate has to interrogate the candidate directly.

**Background jobs and the advisory lock.** Blue-green's premise is that two versions are alive at once, which is safe for request handling (Caddy sends traffic to exactly one) but not for the periodic loops: the alert monitor (30s, and it *sends notifications*, with its `firing` de-dup state held per-process, so a second instance re-fires everything already firing), the eval meter, the vocabulary and behavioural refreshes, the corpus refresh and the metrics rollup — the last four all run once at boot, so a standby colour would burn CPU on a 1-core VM at exactly the moment its health check needs to pass. `internal/shared/leader` solves this with a Postgres session-scoped advisory lock (`pg_try_advisory_lock`): the composition root registers every background start through `App.whenLeader` and only runs them once the lock is won. This works **only because the Supabase URL uses the session-mode pooler on 5432** — over a transaction-mode pooler (6543) a session-scoped advisory lock is not safely held across statements. It is self-healing: leadership is released when the process exits or its connection drops, and the standby's 10s retry picks it up, so a crash cannot leave the jobs unowned. Note the acquisition scheduler is *not* in this set — it is request-driven, not a cron, so it only ever acts on requests its own colour received.

Closest manifest entry is **Singleton** (`go/creational-patterns-in-go/singleton-pattern`, *Cost:* "Global state can leak across tests"), and it loses precisely because it scopes uniqueness to a process — under blue-green that yields exactly two of the thing that must be unique. Arbitration has to live somewhere both processes can see, which is the database.

**Container healthcheck.** `deploy/Dockerfile` gained a `HEALTHCHECK` (busybox `wget` against `127.0.0.1:8000/health`, 10s interval, 30s start period) so Docker itself knows a colour's state — previously Caddy proxied blind.

## The deploy/ move (2026-07-25)

Every deployment artifact moved from the module root into `deploy/`: `Dockerfile`, `Caddyfile`, `caddy/`, and `docker-compose.prod.yml` → `compose.prod.yml`, joining the scripts already there. The workflow's SSH step is unchanged (`bash deploy/blue-green.sh`), and both scripts still `cd` to the module root, so every path in `lib.sh` is simply one level deeper. Three things about that move are not obvious:

**The project name had to be pinned.** Compose derives its project name from the compose file's parent directory, so relocating the file would have renamed the project `go-api` → `deploy`. Container names are explicit and would have collided with the running ones; `caddy-data`/`caddy-config` are *not* explicit, so they are project-prefixed and would have been abandoned — Caddy would have started with an empty cert store and re-requested certificates against Let's Encrypt's rate limit. `name: go-api` at the top of `compose.prod.yml` preserves the pre-move identity, and dropping it re-opens exactly this failure.

**The live upstream file could not move with the repo.** `caddy/upstream.conf` is gitignored VM state, so `git pull` does not carry it to `deploy/caddy/`. Absent a shim, the first post-move deploy would have found no upstream file, fallen through `seed_upstream_if_missing` to the blue default, and — if green happened to be live — "deployed" by rebuilding the colour already serving, destroying the zero-downtime guarantee for that one run. `LEGACY_UPSTREAM_FILE` in `lib.sh` adopts (`mv`s) the pre-move file when the new path is empty, and `blue-green_test.sh` covers it. It is dead weight after the first successful deploy and is marked for deletion in `services/go-api/CLAUDE.md`.

**One brief Caddy recreate is expected.** The caddy service's bind-mount sources changed, so the first `compose up -d redis caddy` after the move recreates that container — a few seconds where the site is not answering, once. The API colours are untouched by it.

**Gotchas**: (1) schema migrations are still explicitly NOT applied by the pipeline — the workflow only emits a warning annotation listing changed files under `services/go-api/migrations/`, expecting manual `psql`. Blue-green *raises* the stakes here: both versions run against one database during the swap, so a migration must stay compatible with the outgoing version (expand/contract) or the drain window breaks it. (2) `command_timeout: 20m` on the SSH step — a build hanging past 20 minutes fails the run mid-flight; the live colour keeps serving, but the candidate may be left running and should be stopped by hand. (3) Production Redis has zero persistence by design (cache-only, regenerable). (4) The build still happens on the VM, so deploys are slow on a small box; moving to a registry (CI builds, VM pulls by SHA) is the next step if that becomes the bottleneck — the blue-green mechanics do not change, only where the image comes from. (5) The first run after this change leaves the legacy `altune-go-api` container orphaned; the script force-removes it after a successful flip.

## Acquisition tooling in the image (2026-07-26)

The runtime image gained two dependencies: the Alpine `chromaprint` package (providing `fpcalc`, for acoustic fingerprinting) and the `streamrip` pip package (providing `rip`, for catalog-resolved fetches), alongside the existing ffmpeg and yt-dlp. Both are inert without configuration — `ACOUSTID_API_KEY` gates the first, `STREAMRIP_SERVICES` the second — so a deploy that ships the binaries before the env vars simply doesn't use them.

Two operational gotchas. Streamrip's Deezer support needs an account **ARL cookie** configured on the VM via `rip config open`; until it is present, `streamrip:deezer` fails at fetch time, which the source registry logs as a warning and routes around (one source failing never fails a search) — the symptom is log noise plus no Deezer fetches, not a broken acquisition. And the ARL expires periodically, so a previously working Deezer path can go quiet without any deploy having happened; the same warning is the signal to refresh it.

### Streamrip credentials must be host-mounted

The container runs as `altune` (uid 1000) and streamrip reads `/home/altune/.config/streamrip/config.toml`. Containers are recreated on every blue-green swap, so a config written inside one is lost — `compose.prod.yml` therefore bind-mounts `/home/ubuntu/altune/streamrip.toml` over that path, following the same pattern as `cookies.txt`. The mount is read-write on purpose: streamrip persists refreshed credentials (Tidal tokens) back to its own config, and a read-only mount would break that. Both colours share the one host file, which is correct — it is credentials, not state.

Deezer quality is counter-intuitive and worth stating plainly. With `use_deezloader = true` and **no** ARL, streamrip fetches free 320kbps MP3 via deezloader. Supplying an ARL disables deezloader entirely, so an ARL from a *free* Deezer account yields 128kbps — strictly worse than not configuring one. Only a premium ARL is an upgrade, and only with `quality = 2` (FLAC); the default config ships `quality = 2` already, which silently degrades to 320 for deezloader users. An ARL is a full account session token, expires after weeks to months, and is invalidated by logging out of the browser session that produced it.
