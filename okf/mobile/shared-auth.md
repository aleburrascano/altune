`supabaseClient.ts` is the app's single `createClient` call (ADR-0006), promoted from `features/auth/api/` once 2+ features depended on it (api-client, playback); every consumer — including the auth feature itself — imports it from here directly (the old feature-local re-export is gone). Session persistence is `expo-secure-store`, NOT `AsyncStorage` (Risk-#3 in the auth-integration spec), via an adapter that maps Supabase's storage interface to SecureStore's async API. Two load-bearing details: `keychainAccessible: AFTER_FIRST_UNLOCK` lets the SDK read tokens when the app wakes in the background on a locked device — the default `WHEN_UNLOCKED` fails the auto-refresh tick with "User interaction is not allowed" — and `getItem` catches SecureStore throws and returns `null` (for tokens stored before that change), which the SDK treats as "no session" and re-authenticates. Web falls back to `localStorage` (or a no-op store), config is `persistSession: true`, `autoRefreshToken: true`, `detectSessionInUrl: false`, and credentials come from `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY`. Invariant: this is the only file that value-imports `@supabase/supabase-js`; everything else takes the singleton, and only `useSession.ts` here (plus feature code) may `import type` from the package.

`useSession.ts` (promoted because auth's AuthGate and settings both consume it) subscribes to `supabase.auth.onAuthStateChange` and exposes the discriminated union `SessionState = {status:'loading'}|{status:'signed-in',session}|{status:'signed-out'}`, defined in the same file. It also owns the **local-data boundary** for SDK-initiated identity changes: both the initial `getSession` resolution and every auth event flow through one `apply(session)` function that compares the incoming `user.id` against a ref of the last-seen id and, on change, calls `forgetPreviousUsersLocalData` — `queryClient.clear()`, `clearSessionExpired()`, and (since 2026-07-24) `usePinnedStore.getState().unpinAll()`, which deletes the previous account's offline audio from the document directory. Offline downloads are not user-scoped on disk, so this hook is the only thing that reclaims them — but the harm it prevents is disk residue and a Settings screen reporting the previous user's download count and size, *not* cross-account playback: pinned files are keyed by track UUID and another account's library never names one (see [shared-offline](shared-offline.md)). Despite the name, `forgetPreviousUsersLocalData` deliberately leaves the playback prefetch cache alone — it is OS-purgeable and UUID-keyed, and `shared/` may not import from `features/`, so reaching it would need the composition root. Do not "complete" this function by importing `features/playback` here; the eslint boundary rule will reject it, correctly. This exists because `queryClient.clear()` in `useSignOut` covers only the explicit Settings sign-out — an SDK-emitted `SIGNED_OUT` (refresh failure) or a `setSession` user swap (deep link) bypasses it, leaving user A's cached library readable by user B. Clearing happens on identity CHANGE only, never on every event: `TOKEN_REFRESHED` fires with the same user and must not wipe the cache (asserted in `__tests__/useSession.test.ts` — pending rebuild per [test-taxonomy](../playbooks/test-taxonomy.md)). A separate `seededRef` distinguishes "haven't seen anything yet" from the real identity `null` (signed-out), so the first observation never clears.

Two guards in `apply` exist because the `Session` it receives is less trustworthy than its type claims. **A session carrying no `user` object is treated as no session at all**, not as a signed-in session with a null identity: the SDK's own `_isValidSession` (`GoTrueClient.js`) admits any stored blob holding `access_token`, `refresh_token` and `expires_at`, and never checks `user` — so a keychain entry written by an older version reaches `apply` with `user` undefined, where the un-optional `session?.user.id` read threw a `TypeError` and `SettingsScreen`'s `session.user.email` would have thrown next. And the `getSession()` **`.catch` arm only applies when nothing has been seeded yet**. It exists to stop a failed cold-start read from stranding `AuthGate` on the splash screen forever; applied unconditionally it did the opposite of its purpose, because `onAuthStateChange` fires synchronously on subscribe, so a later rejection would wipe the cache and downloads of a user the listener had already confirmed. Note this makes `getSession()` rejection a reachable state despite [shared-api-client](shared-api-client.md)'s claim that it never throws: `__loadSession` awaits `_removeSession()` inside a `try`/`finally` with no `catch`, and the storage adapter's `removeItem` does not swallow a keychain failure.

`sessionExpired.ts` is the one feedback edge from HTTP 401 back to auth state. The SDK is the sole authority on session validity but only knows what it sees locally — when the backend rejects a token the SDK still holds (server-side revocation, JWKS rotation, clock skew), no `SIGNED_OUT` is emitted and every query 401s forever. `apiFetch` — the single choke point for every JSON /v1 call (see [shared-api-client](shared-api-client.md); playback's `api/audio.ts` routes its JSON calls through it too, keeping raw fetch only impossible for the native player's own stream requests) — calls `markSessionExpired()` on a server 401; `AuthGate` reads `useSessionExpired()` and renders `SessionExpiredNotice` to offer explicit re-auth. It is a module-level `useSyncExternalStore` store rather than React context because the producer (`apiFetch`) lives outside the React tree. Marking is deliberately NOT acting — no auto-sign-out on 401, because a server-side JWKS/config blip would bounce every user mid-session at once; the user chooses when to re-authenticate (silent session resurrection is out of scope, see docs/specs/auth-hardening/spec.md). `clearSessionExpired()` resets the flag and is called by `useSession` whenever identity changes. It also exports `_listenerCountForTest()`, which exists for one reason: without it, nothing could observe whether `subscribe`'s cleanup actually ran. A cleanup replaced by `return () => {}` left the entire repo's suite green — React's `useSyncExternalStore` listener for an unmounted fiber is a silent no-op in this version, so a leaked listener and a released one were indistinguishable through every public surface, while the module-global `Set` grew a dead closure per mount for the app's lifetime. This is the same class of hole as the `expo-file-system` double's `write() {}` in [ADR-0020](../../docs/adr/0020-test-taxonomy-and-ratchet-gates.md): code whose state cannot be read cannot be constrained.

`useSignOut.ts` (promoted because settings and library/ProfileSheet both consume it) drops the Supabase session AND clears the React Query cache in one motion: `supabase.auth.signOut()` then `queryClient.clear()` — the AC#5(b) half, since a stale cached result from user A leaking to user B would be a multi-tenancy bug at the cache layer. The cache is cleared even when `signOut` errors or throws. It returns a typed `SignOutResult` union (`idle|pending|ok|error`), never boolean flags. Invariant: this hook only covers *explicit* sign-outs; SDK-initiated identity changes (refresh-failure `SIGNED_OUT`, deep-link `setSession` user swaps) bypass it entirely, so `useSession` above owns the complementary half, clearing the cache on any user-id change (and never on same-user `TOKEN_REFRESHED`). Together the two guarantee the cache never carries across identities regardless of which side initiated the change. Offline downloads are **not** symmetric this way: `useSignOut` never calls `unpinAll`, so an explicit Settings sign-out reclaims disk only because Supabase then emits `SIGNED_OUT` and the root-mounted `useSession` observes it. That indirection is load-bearing for the commonest sign-out path and is not covered end-to-end by a test — the "SDK-initiated sign-out" case invokes the auth callback directly.

Tests live in `__tests__/` here, rebuilt blind on 2026-07-31 per [test-taxonomy](../playbooks/test-taxonomy.md); the per-category verdict is [okf/testing/shared-auth.md](../testing/shared-auth.md). `supabaseClient.test.ts` drives the real storage adapters through the `expo-secure-store` double by capturing the options object the module hands `createClient`, and pins the whole `auth` config block — `autoRefreshToken` and `detectSessionInUrl` were both silently mutable before it did. `sessionExpired.test.ts` / `.tsx` split the store's transitions from its `useSyncExternalStore` wiring and its listener bookkeeping. `useSession.test.tsx` covers the identity matrix, the adversarial session shapes and both seed-versus-listener orderings, with `useSession.property.test.tsx` stating the whole thing as one generated law: the wipe fires exactly once per adjacent distinct pair, never on the first observation and never on a repeat. `useSignOut.test.tsx` pins the three settled outcomes plus the ordering constraint that the cache clear must follow the SDK call, not precede it. `authContract.test.ts` derives the 401-versus-503 split from the Go middleware source at test time, and `acceptance.test.tsx` carries AC#4 and AC#5(b). The session-expired flow will additionally be exercised through `features/auth`'s own tests once that slice is rebuilt.
