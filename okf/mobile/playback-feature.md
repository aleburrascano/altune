Owns audio playback end-to-end: mini/full player UI, the native queue, lock-screen controls, download-ahead caching, server-side queue resume, and behavioral telemetry. The central design constraint is that `react-native-track-player`'s top-level import touches a native module Expo Go doesn't bundle — importing it unconditionally would crash the app in Expo Go.

**Provider selection** (`hooks/PlaybackProvider.tsx`): a session-constant `isExpoGo` flag chooses which provider implementation to `require(...)` — `expoGoPlaybackProvider.tsx` (no-op, audio inert, `console.warn`s on play) or `trackPlayerProvider.tsx` (the real backend) — using `require` rather than a static `import` specifically so the unused module's native import is never touched. Because the choice is constant for the session, there's no hook-order risk from branching. `expoGoPlaybackProvider` still drives the Zustand queue store (see [shared-playback](shared-playback.md)) on skip so screens remain testable without a dev build.

**TrackPlayerPlaybackProvider** (`hooks/trackPlayerProvider.tsx`) is the real implementation. The public `PlaybackState` (`idle|loading|playing|paused|ended|error`) is now a pure function, `derivePlaybackState.ts`, extracted so the position rules are unit-testable; its buffering branch preserves `positionMs` instead of resetting to 0 — the fix for the resume "flicker" where priming the queue slammed the scrubber to 0:00 before jumping back. Position handling is layered: before native progress goes live (progress 0), the store's `resumePositionMs` seed is displayed so the scrubber lands at the saved offset on relaunch; the moment `livePositionMs > 0` the seed is retired (native progress returns to exactly 0 at the top of *every* track, so a lingering seed would reappear as a jump at each track start). While backgrounded (`useIsForeground`), the display position freezes so the memoized state keeps its identity — the fix for iOS's background-CPU watchdog — and the whole context value is now `useMemo`d so that optimization actually propagates (a bare object literal would re-render every `usePlayback()` consumer twice a second regardless). `seekTo` routes through `seekControls.ts` (`seekPreservingPlayback`): iOS RNTP doesn't reliably re-emit `Playing` after a seek, so `play()` is re-asserted when the track was playing (guarded so scrubbing a paused track never starts audio). `play()` clears the queue store in the same tick as `loadNativeTrack`'s `reset()` so the store never describes a queue the player no longer holds. New best-effort context methods `reorderUpcoming`/`appendToQueue`/`insertNext` mirror store-side shuffle/Add-to-Queue/Play-Next into the native queue; failures are swallowed because the store's play order is already updated and re-syncs on the next queue rebuild.

**Native queue loading, load tokens, and the sync guard** (`loadNativeTrack.ts`, `nativeSyncGuard.ts`): `loadNativeQueue` loads the **entire** ordered queue in one pass so transitions are native and gapless. A load is a multi-await sequence (setup → resolve URLs → reset → add → skip), so every load claims a last-write-wins `loadToken` and bails after each await if a newer load claimed one — the newest caller wins, so a user tap always beats an in-flight resume instead of interleaving `reset()`/`add()` into a mixed queue. Library tracks stream via short-lived presigned URLs minted by `fetchAudioUrls` (`api/audio.ts`, POST `/v1/audio-urls` through `apiFetch` — like `recoverAudio`, so a server 401 marks session-expired; only `audioRequestHeaders` for the native player’s own stream requests stays outside the choke point — with a 2.5s abort so a slow sign never blocks queue start) — direct from storage instead of proxying every byte through the API — capped at `MAX_PRESIGN` (25) from the start index; everything else falls back to the authenticated proxy URL. A single `toNativeTrack` builder (`nativeTrack.ts`) turns a `PlaybackTrack` into the native entry via this presigned-else-proxy ladder (a `streamUrl` option overrides it with a resolved presigned URL or a downloaded local path) — shared by the queue loader here and the download-ahead repair path (`audioPrefetch.ts`), so the mapping lives in exactly one place. It also stamps `id: trackKey(track)` on every entry — the identity the whole reconciliation story below depends on, and the reason it must stay the single builder — and *omits* `artwork` entirely when a track has none, rather than sending `''`: an empty string is a present-but-invalid URL to the platform now-playing layer, not an absent one. (In-app rendering was never affected; the `Artwork` primitive already takes `uri: string | null`.) `nativeSyncGuard.ts` pins the target index during a load and drops the spurious index-0 `PlaybackActiveTrackChanged` transient that `TrackPlayer.add` emits while priming; it releases on the *first real* index rather than an exact target match, so a missed target can never pin the guard forever and silently drop later transitions. `reorderUpcomingNative` replaces only tracks after the active one (`removeUpcomingTracks` + re-add) so audio continues untouched and native index keeps mirroring store play order; `appendNativeTrack`/`insertNativeTrackNext` do the same for single-track edits. Diagnostic-only timing instrumentation for a reported "playback feels slow" investigation stamps a `marks` object (`start`, `headers`, `resolve`, `added`) at each await boundary in both loaders; `logTimeToPlaying` then attaches a one-shot `PlaybackState` listener that, once `State.Playing` is reached under the same load token, logs the elapsed time from `marks.start` via `console.log('[audio-timing] ...')` — self-cleaning after 15s if playback never starts (autoplay=false, load error, an early pause). It is console-only, not wired into the behavioral telemetry pipeline below, and safe to delete once the investigation resolves.

**Download-ahead cache** (`audioPrefetch.ts`): RNTP's iOS backend does not pre-buffer the next queue item, so every auto-advance stalled ~1s. On each active-track change the *next* library track is downloaded to an `expo-file-system` cache dir and its still-upcoming native entry is swapped to the local path, so the boundary loads from disk with zero buffering. Invariants: only entries strictly **after** the live native active index are ever swapped (RNTP activates the next track when the active one is removed — swapping the playing track skips it, audible as the next button jumping two tracks), and a failed re-add must restore a streaming entry (a missing slot offsets every later native index from the store). `swapUpcomingToLocal` therefore takes no index at all: it reads the live native queue and active index and locates its own slot by the entry's `id` (`trackKey`), so a caller's stale idea of where a track sits can never remove the wrong one — the failure mode under fast skipping, where the queue was re-indexed between deciding to prefetch and performing the swap. If both the local re-add and the streaming restore fail, the hole is reported through `playbackErrorStore` under that track's key instead of being swallowed; the identity-based reconciliation in [shared-playback](shared-playback.md) keeps the hole from corrupting anything beyond that one track. `repairActiveToStreaming` likewise re-checks `getActiveTrack()` before calling `TrackPlayer.load` — it replaces whatever is active, so firing it for a track that is no longer playing would reload (and restart) a healthy one. Eviction keeps current+4 (`KEEP_WINDOW`) tracks; the `swappedToLocal` set lets the error path distinguish "our cache evicted the file" (repair in place via `TrackPlayer.load`, `repairActiveToStreaming`) from "the server's file is really gone" (`recoverAudio`, POST `/v1/tracks/{id}/audio/recover`, needed because presigned streams bypass the proxy's missing-file recovery). Every path is best-effort: failure leaves the streaming URL playable. `prefetchNext` carries its own independent diagnostic timing (same `[audio-timing]` console-log convention as `loadNativeTrack.ts` above, but no shared code — no `TimingMarks`/`logTimeToPlaying`): a cache hit logs `cache=hit swap_ms=<n>`, and a cache miss separately times the presigned-URL resolve and the `File.downloadFileAsync` download, logging `cache=miss resolve_ms=<n> download_ms=<n> total_ms=<n>` — console-only.

**Service** (`service.ts`, registered outside Expo Go in the root layout): forwards lock-screen remote events to the native player; `RemotePrevious` matches the in-app previous button (restart when past `RESTART_THRESHOLD_MS`, else step back), reading position from the native player because the JS-side position is frozen in background. `PlaybackActiveTrackChanged` is filtered through `shouldApplyActiveIndex` (the sync guard) before mirroring into the store's `syncCurrentIndex` — passing the event's `track.id` alongside the index so identity settles any disagreement — then logs a diagnostic `track-transition index=<n> at=<timestamp>` line (console-only, correlated against `prefetchNext`'s own timing above) and kicks `prefetchNext` off the *reconciled* store index rather than the raw native one.

`PlaybackError` routes to the repair/recover split above, but only after establishing *which* track failed. The RNTP payload is just `{code, message}`, so the handler resolves the culprit from `getActiveTrack()` and matches its `id` against the queue, falling back to the store's current track only when native reports no identity at all. Reading the store directly (the earlier behavior) was wrong whenever the error arrived after the cursor had moved — routine under fast skipping, and under RNTP's read-ahead, where the failure surfaces for a track the user has already left. The consequences were concrete: `recoverAudio` was POSTed for an innocent track, and `repairActiveToStreaming` reloaded and restarted whatever happened to be playing — one unplayable track visibly breaking the ones after it.

**Error surfacing** (`playbackErrorStore.ts`): a Zustand store holding a single `{key, message}` pair, where `key` is a `trackKey`. It is the one channel for playback failure — the provider no longer keeps `errorMessage` in local state, it derives it by matching the store's key against the displayed track, and both load failures (`play`/`startQueue` catching) and native `PlaybackError`s report into it. Two bugs close together here: native errors previously never reached `PlaybackState` at all (only thrown load errors did), so a track that failed to decode sat on `loading` forever with no `status: 'error'` and no retry affordance; and the provider cleared `errorMessage` on every `currentQueueTrack` change, so even a surfaced error was wiped by the next transition. Keying the error by track makes the clear-on-change unnecessary — an error for track A is simply not shown while track B is current — and `retry`/`stop` clear it explicitly.

**Queue resume** (`hooks/useQueueResume.ts`, pure helpers in `resumeQueue.ts`): the queue persists server-side (`saveQueueState`) every 15s and on backgrounding — track ids in **play order** with `current_index` pointing into that same list, plus `natural_order` (pre-shuffle) so restore rebuilds the exact shuffled sequence *and* can un-shuffle back; `source_id` wire format is `library` / `playlist:<id>:<url-encoded name>` / `search[:<url-encoded query>]` (encoding so a `:` in a name can't be mistaken for a separator). Restore is two-stage: the server embeds the current track's metadata, so a one-track placeholder queue renders now-playing instantly (its store generation is pinned in `placeholderGenerationRef` so the periodic save can never overwrite the real saved queue with it), then the full library is rehydrated via `getTracks` and the play order reconstructed (`reconstructPlayOrder`; non-ready tracks are dropped, so the current track is relocated by id, not raw index — `resolveResumeStartIndex` clamps for legacy rows). Ownership is generation-based: after every await, resume compares the store's `generation` against the one it last wrote and aborts if the user took over — a tap during resume must win, never be silently replaced by yesterday's queue. Finally the native player is primed with the full queue paused (`autoplay: false`) at the saved position, and `setResumePosition` seeds the scrubber until live progress arrives.

**Behavioral signals**: `signals.ts` holds pure helpers — `listenThresholdMs` (30s OR 50% of duration, Kim WSDM 2014) and `buildTrackPayload` — consumed by `usePlaybackSignals` to fire `play`/`completed`/`skip` events without polluting the provider with telemetry logic (see [telemetry](../backend/discovery/telemetry.md) on the backend side). Signals read the raw live position, not the display position, so the resume seed can't spoof the listen threshold.

**UI**: `ui/FullPlayer.tsx` is the fullscreen modal (shuffle and repeat both driven through the `useQueuePlayback` facade so the native queue follows the store, next button disabled when `!hasNext`, scrubber, retry-on-error). `ui/Scrubber.tsx` is a proper `accessibilityRole="adjustable"` control — beyond the pan-drag it exposes `increment`/`decrement` accessibility actions (±15s) so VoiceOver/TalkBack can move playback position, not just announce it. `ui/QueueSheet.tsx` shows a raised Now Playing surface panel + Up Next rows, and drives skip-to / remove / clear-upcoming through the same facade — never the store or native controls directly (that lockstep is the facade's job, see [shared-playback](shared-playback.md)): each row pairs swipe-to-remove with a trailing ⋮ `IconButton` opening an `ActionSheet` of Move to Top / Move Up / Move Down / Remove from Queue (the reorder options hide at the ends), so reorder and removal are both reachable for screen-reader / motor-impaired users rather than gesture-only; reorder routes through the facade's `moveQueueItem` (store `reorderQueue` → native `reorderUpcoming`, the same lockstep shuffle uses — drag-to-reorder is intentionally not built because expo-audio queue behavior can't be verified on the web test target); rows are keyed by `trackIndex` (the entry's slot in `tracks`), not play-order position, because play-order keys shift on every advance and remounted rows inherited swiped-open state; the facade's clear-upcoming reads the store at press time, not from the render closure, because the confirm Alert can sit open across auto-advances and a stale `currentIndex` would delete the playing track. All three players (mini/full/queue) render featured artists via `withFeaturing`. The unified bottom dock — the in-flight downloads bar stacked over `ui/MiniPlayer.tsx` — is composed at the tab shell (`app/(tabs)/_layout.tsx`), the one place that may depend on both the acquisition subsystem and this feature; the download views themselves live with their data in [shared-acquisition](shared-acquisition.md).

## Lyrics (2026-07-24)

`/player/lyrics` is a modal over the full player, fed by `GET /v1/discovery/lyrics` (Deezer-backed, tracks only, keyed on title + artist). The server had served this since before the client surface existed: the earlier Discogs/Deezer/Lyrics enrichment components were deleted in the 2026-07-16 structure audit because nothing rendered them, with the note that lyrics belong to the full player when it lands. It has landed.

Time-synced lines are the good case and the default: the active line is highlighted and the view follows playback, and tapping a line seeks to it (`activeLineIndex` is a linear scan — ~60 entries, run on a position tick, so the constant factor is irrelevant and the boundary behaviour stays obviously correct). Plain text is the fallback. Line offsets are captured via `onLayout` rather than computed, because lyric lines wrap and there is no fixed row height to derive them from; the follow-scroll respects `useReduceMotion`.

`_lyricsView` is the five-state machine (`loading | error | unavailable | synced | plain`). The load-bearing case is `unavailable`: the endpoint answers 200 with an empty payload for anything it cannot resolve, so an empty body must never render as an error. Writer and copyright credits render under every non-empty view — a licensing requirement of the provider, not decoration.

## Sleep timer and playback speed (2026-07-24)

Both live behind one overflow sheet in the full player (`PlayerOptionsSheets`), which shows each setting's current value on its root row so the state is readable without drilling in. `ActionSheet` fires `onPress` then unconditionally `onClose`, so a drill-down row cannot simply `setSheet('speed')` — the close in the same batch would wipe it; the root records the target in a ref and its close handler reads that instead of dismissing.

The **sleep timer** (`sleepTimerStore`) stores an absolute `endsAt`, never a decrementing remainder: JS timers are throttled or suspended while backgrounded, so a counter would drift or freeze. `SleepTimerBridge` mounts inside `PlaybackProvider` at the app root — not in `FullPlayer`, which unmounts — and re-checks the deadline on every foreground transition, firing immediately if it has already passed.

**Playback speed** adds `setRate` to the `PlaybackControls` contract (RNTP's `setRate` in the real provider, a no-op in the Expo Go one). The chosen rate lives in `playbackRateStore` so the label survives the player closing; RNTP holds the rate on the player rather than the track, so it persists across track changes within a session, which is what a speed control is expected to do.

**Offline playback (2026-07-24).** `loadNativeTrack.signedUrl` is the single seam where a library track's URL is chosen, and it now prefers a pinned local file over the presigned URL, with the authenticated proxy still last. The pinned check goes first deliberately: once a track is on disk, playback must not depend on a signed URL that expires or a network that is not there. See [shared-offline](shared-offline.md); note it is a different concern from `audioPrefetch`, which is a cache-directory optimisation the OS may purge.

**TestID (2026-07-24).** `MiniPlayer`'s root carries `testID="mini-player"`. It had none, and it is the observable that proves playback actually started in the `search-save-play` e2e flow — the dock appearing above the tab bar is the only user-visible confirmation that audio is playing.

## Structured queue source (2026-07-25)

`useQueueResume` used to pack and parse the queue's origin itself: `buildSourceId` produced `playlist:<id>:<url-encoded name>` and `parseSourceId` picked it apart on restore, with a `decodeOrEmpty` guard for malformed input. That format is the server's, and the URL-encoding existed only so a `:` in a playlist name could not be read as a separator.

The wire now carries a structured `source` object and the two functions are a pair of small mappers between it and the store's `QueueSource` union. The packing lives in `playback/domain/queue_source.go` (see [playback](../backend/playback.md)).

## Evicting prefetched audio when the recording changes (2026-07-26)

`prefetchNext` caches the next track's audio under `<trackId>.<ext>` and `findCached` resolves it by that id alone — deliberately, since the presigned URL rotates on every resolve and could never be a cache key. The cost surfaced when re-acquire shipped: a replacement lands on the *same* object key, so the id still resolves and `swapUpcomingToLocal` kept feeding the player the old recording. Eviction is by track id for the same reason the cache is: the file's identity is the track, and its content is whatever the server last stored.

`evictCached` deletes the cached file and drops the id from `swappedToLocal`, and is registered into `shared/acquisition/audioCacheInvalidation` by `playbackService()` so `applyServerEvent` can reach it without `shared/` importing this feature. It is registered in the service rather than at module load because the service is already the playback lifecycle entry point, and a registration that happened on import would fire in every test that touches the module graph.
