The user's personal collection screen (`docs/superpowers/specs/2026-06-28-library-redesign-design.md`). Model: **spine + lenses** — the Tracks and Playlists chips are what the user owns (primary, fetched/mutated), while Albums and Artists are client-derived groupings of saved tracks (lenses, no backend endpoint). `ui/LibraryScreen.tsx` is the orchestrator: it owns the active `LibraryChip` (`'playlists'|'tracks'|'albums'|'artists'`, opens on Playlists), a per-chip sort key, search, and the track context menu, and renders header → search → chip bar → sort control → the one active view — no stacked overview, selecting a chip swaps only the content area. (The chip/list vocabulary was renamed songs→tracks in the 2026-07-16 structure audit — `Track` is the glossary noun; "song" is banned.)

**Data — SSE-patched, not polled**: `hooks/useLibraryHome.ts` fetches all tracks in one page (`limit: 2000`) under `libraryKeys.home` (`['library-home']`) with `staleTime: Infinity` — SSE events from `@shared/events` keep the cache coherent by patching it in place (`trackCachePatch.ts`: `patchTrackInCaches`/`upsertTrackInCaches`/`removeTrackFromCaches` write library-home and every `['playlist']` detail at once), so the query never background-refetches on mount/nav (F15). Query keys come from `@shared/lib/query-keys` (`libraryKeys`/`playlistKeys`) — the cache topology's single declaration; the audit's F3 found the retired `['library']` infinite cache still being patched everywhere precisely because keys were stringly duplicated (the dormant `hooks/useLibrary.ts` shell and every `['library']` ghost branch were deleted). The old 5s pending poll was degraded to a 60s belt-and-suspenders `refetchInterval` while any track's `acquisition_status` is `pending` (F14) — a missed terminal acquisition event (see [pipeline](../backend/acquisition/pipeline.md)) still reconciles without the churn. Pull-to-refresh was removed from all four views; the error screen's Retry button is the manual escape hatch. The playlist queries follow the same pattern: `hooks/usePlaylistActions.ts`, `ui/AddToPlaylistSheet.tsx`, and `ui/PlaylistDetailScreen.tsx` all set `staleTime: Infinity` because rename/remove/reorder events patch them. **Cache-writer invariant**: because `staleTime: Infinity` pins whatever is written, writers must never fabricate a library snapshot from an absent cache — `undefined` means errored (stale-token 401) or never fetched, NOT empty (`{items: []}` is empty); the detail feature's optimistic save insert once seeded a `total: 1` library over an error state and pinned the lie for the session (`features/detail/save-cache.ts`, see [detail-feature](detail-feature.md)). All patch helpers no-op on absent caches. `hooks/useLibraryGrouping.ts` derives `AlbumGroup`/`ArtistGroup` from the flat track list via `@shared/lib/derive-library-groups` — pure client-side grouping, not domain types. `state.ts`'s `_viewForState` is the same pure loading > error > empty > list precedence pattern used across features.

**Playlist writes have one owner**: `hooks/usePlaylistMutations.ts` holds every playlist mutation (create, create-with-track, add-track, rename, delete, remove-track) with a uniform policy — optimistic patch where sensible, rollback to the onMutate snapshot, `Alert.alert` on failure, invalidate on settle. Before the 2026-07-16 audit (F1) the six mutations lived in three files and had diverged: the LibraryScreen create path failed silently while the sheet's create alerted. Screens keep only their local UI state and pass navigation/modal-closing via mutate-level callbacks. `ui/CreatePlaylistModal.tsx`'s name field routes through the shared `TextField` primitive (see [shared-ui](shared-ui.md)); it and `ui/AddToPlaylistSheet.tsx` give their dismiss backdrops an accessible `Close` label. The add-to-playlist sheet holds its "Added ✓" confirmation ~700ms before auto-closing (the timer is cleared on unmount) — it previously cleared the flag the same tick it set it, so the confirmation never rendered — and stays open on error so the user can retry.

**Search — a filtered library must never look like a missing one**: `hooks/useLibrarySearch.ts` debounce-commits at ≥2 chars and clears the committed query *immediately* whenever the trimmed input drops below the threshold — the old code handled length 0 and ≥2 but not length 1, so deleting down to one character kept the stale query silently filtering the whole library, which users read as "my library is gone" (the 2026-07-14 report; `__tests__/useLibrarySearch.test.ts` — pending rebuild per [test-taxonomy](../playbooks/test-taxonomy.md)). The hook exposes the committed `query` string so `ui/LibraryNoResults.tsx` (rendered by `LibraryScreen` when `search.hasQuery && active.count === 0`) can name the query, state the library is intact, and offer a one-tap clear. The per-view `emptyLabel`s are now the plain "No tracks yet"-style copy only — search-empty is handled exclusively by `LibraryNoResults`.

**Mutations are event-driven, not invalidate-driven (F17)**: `hooks/useDeleteTrack.ts` optimistically removes the track from `libraryKeys.home` (with rollback + `Alert.alert` on error) and performs *no* invalidations — the server's own `track_deleted` event echoes back and removes the row from every other cache. `LibraryScreen` gates the "Remove from Library" menu action behind an `Alert.alert` confirm before firing the mutation — matching Clear Queue and Delete Playlist, so every destructive action is guarded (the removal was previously the one unguarded, un-undoable path). `hooks/useRetryAcquisition.ts` likewise dropped its four invalidations: `onMutate` optimistically flips the row to `pending` (clearing `failure_reason`) across all caches via `patchTrackInCaches`, and the re-queued acquisition's SSE events (started → progress → completed/failed) drive the rest.

**Rows and menus**: `ui/LibraryRow.tsx` shows a live download phase caption (`useDownloadPhase` from `@shared/acquisition/downloadStore` + `phaseLabel`) whenever a download is in flight, *regardless* of the cached `acquisition_status` (F7) — so a re-acquired ready/failed track shows progress too, falling back to the plain pending caption otherwise. The artist line renders `withFeaturing(track.artist, track.featured_artists)`. The row subscribes to two live stores keyed by its own track id — `downloadStore` for the phase caption and `pinnedStore` for the offline check/arrow — which `__tests__/LibraryRow.liveness.test.tsx` — pending rebuild per [test-taxonomy](../playbooks/test-taxonomy.md) pins by mutating each store and asserting the row moves without a re-render from above, including that a *different* track's activity leaves it alone. That test is the template for the standing rule (`apps/mobile/CLAUDE.md`) that any component displaying server-mutable state owns a liveness test; the offline assertions read the row's `accessibilityLabel` rather than the icons' testIDs, because a lucide glyph does not forward `testID` through the test renderer. The ⋮ button measures itself with `measureInWindow` and passes a `MenuAnchor` up to an anchored `ContextMenu` (`@shared/ui/primitives/ContextMenu`). The menu itself is assembled by `ui/trackMenu.ts` (`buildTrackMenuItems`) — the audit's F2 found three drifted copies across `LibraryScreen`/`PlaylistDetailScreen`/`FeaturingScreen`. Invariant part: Play Next / Add to Queue ready-gated, then View Details, then a danger row; per-screen parts: the danger action (Remove from Library vs Remove from Playlist), the details navigation, and Add to Playlist (only the Library tracks list offers it).

**Playlist detail**: `ui/PlaylistDetailScreen.tsx` (route `/library/playlist/[id]`) fetches one playlist by id (`playlistKeys.detail`) and uses the `usePlaylistMutations` hooks — rename and remove-track are optimistic with rollback, delete is mutate-then-navigate-back — each alerting on failure. Play/shuffle build a playable queue via `buildPlayableQueue` and hand it to `useQueuePlayback` (see [shared-playback](shared-playback.md)).

**Featuring**: `ui/FeaturingScreen.tsx` (routes `/library/featuring` and `/discover/featuring`, both thin re-exports) lists the user's saved tracks crediting a featured artist via `hooks/useTracksFeaturing.ts` (`libraryKeys.featuring(key)` where key is mbid, else `dz:<deezer_id>`, else `name:<name>`; `staleTime: 60s`). It navigates within whichever tab stack it lives in (derived from `useSegments`) so back returns to the launching detail screen, and its empty state never dead-ends — it searches discovery for the artist and opens their detail.

**Navigation**: tracks/albums/artists build a `DiscoveryResult` shape and navigate to `/library/detail` through `useLibraryNavigation`, reusing the same detail-handoff seam `discover` uses — the `detail` feature is kind-agnostic about which tab launched it.

Key files: `hooks/useLibraryHome.ts`, `hooks/useLibrarySearch.ts`, `hooks/useLibraryGrouping.ts`, `hooks/usePlaylistMutations.ts`, `hooks/useDeleteTrack.ts`, `hooks/useRetryAcquisition.ts`, `state.ts`, `ui/LibraryScreen.tsx`, `ui/trackMenu.ts`, `ui/LibraryNoResults.tsx`, `ui/LibraryRow.tsx`, `ui/PlaylistDetailScreen.tsx`, `ui/FeaturingScreen.tsx`.

**Offline downloads in the track menu (2026-07-24).** `ui/trackMenu.ts` — still the one assembly point — gains an offline row whose label follows the pinned status (Download / Cancel download / Remove download / Retry download). It sits behind the same `acquisition_status === 'ready'` gate as the queue actions: offline only means something once the server actually holds the audio. See [shared-offline](shared-offline.md).

## Refresh, complete paging, performance and tablets (2026-07-24)

**Pull-to-refresh** now exists on all four lists plus Featuring and playlist detail (`ui/refresh.ts` holds the shared `ListRefresh` shape; `LibraryScreen` builds one that refetches *both* the tracks and playlists queries, since the chips are views over two queries and refreshing half the surface is worse than refreshing none). This closes a real gap: `useLibraryHome` is `staleTime: Infinity` with refetch-on-mount off and a comment claiming pull-to-refresh was the manual escape hatch, but no `RefreshControl` existed anywhere — the only recovery was the error-state Retry, which is unreachable once data has loaded and then gone stale.

**Full-library paging.** `fetch-all-tracks.ts` follows `has_more` to completion. The old single `limit: 2000` request ignored it, so a larger library was silently truncated — and because Albums and Artists are derived client-side from the track list, a truncated fetch rendered *wrong* lenses rather than partial ones. Paging to completion (rather than exposing pagination) is the right shape precisely because grouping, search and sort all need the whole set. It stops on `!has_more` **or** an empty page, so a server stuck on `has_more: true` cannot spin.

**Performance.** `LibraryRow` is memoized on its data fields with an explicit comparator: `renderItem` mints fresh closures every parent render, so the default shallow compare never hits and every row re-rendered (re-measuring its `Artwork`) on each keystroke in the search bar. The comparator's cost is documented on it — a handler whose behaviour starts depending on unlisted state keeps a stale closure. The four filter+sort passes are memoized on the *stable* `search.filter`/`search.matches` identities rather than the search object, which is a fresh literal each render.

**Responsive grids.** `ui/gridColumns.ts` derives column counts from viewport width (covers 2/3/4, avatars 3/5/6). `app.json` declares `supportsTablet: true` while every grid was hardcoded, so an iPad rendered phone-sized cells stretched across a 1024pt canvas. Breakpoints are on width alone, not a device class, so a rotated or split-view window gets the layout its actual width deserves. `FlatList` cannot change `numColumns` in place, hence the `key` remount.

**Honest error copy.** The error view distinguishes offline from a server fault via `isNetworkError`, and a filtered result count is announced to screen readers.

## Shape and deferred scope

The model is spine plus lenses: Tracks and Playlists are what the user owns and are primary, while Albums and Artists are client-side groupings derived from saved tracks (`@shared/lib/derive-library-groups`) — UI read-side lenses, not domain types, with no backend endpoint. The chips are the navigation: selecting one swaps only the content area while search and per-chip sort persist, replacing the old stacked home plus separate `all-tracks` / `all-albums` / `all-artists` routes. "Recently Added" is simply Tracks sorted by Recent rather than a separate section.

`LibraryNoResults` exists because a filtered-out library must never look like a missing one: the 2026-07-14 "entire library is missing" report turned out to be a persisted search filter, so the view names the query, states the library is intact, and offers a one-tap clear.

Deferred deliberately: **Favorites / Liked** is not built, because saving is already the deliberate act — a pinned slot can be added later. **Jump back in / recently played** is a Home concern reserved for a future Home tab, not Library.

## The server owns grouping, search and sort (2026-07-25)

The screen used to page the **entire** track list onto the device (`fetch-all-tracks.ts`, `limit: 2000` until `has_more` went false), pin it with `staleTime: Infinity`, and answer everything from that one array: Albums and Artists were folded out of it by `derive-library-groups.ts`, search was `toLowerCase().includes()` over it, and sort was four `localeCompare` passes. That is why the cache had to be global, why the fold had to be memoized on stable identities, and why `LibraryRow` needed a hand-written comparator — the whole list re-rendered on every keystroke.

All four of those are now server queries, one per chip, each enabled only while its chip is active:

- **Tracks** — `useLibraryTracks` is a `useInfiniteQuery` over `GET /v1/tracks?q=&sort=&offset=`, page size 200, keyed `libraryKeys.tracks(query, sort)`. Paging replaced the fetch-everything loop: a large library now costs one page, not the whole table.
- **Albums / Artists** — `GET /v1/library/albums` and `/v1/library/artists`, keyed `libraryKeys.albums/artists(query, sort)`. `AlbumGroup` / `ArtistGroup` are now wire types from `@shared/api-client/library` (snake_case), not client-derived shapes.
- **Search** — `useLibrarySearch` kept the 300ms / 2-character debounce (UI timing is a client concern) and lost `filter` / `matches`; it now just yields the committed string that goes on the query.
- **Sort** — `ui/sort.ts` kept the `*_SORT_OPTIONS` label lists and lost the comparators. The keys (`recent` / `az` / `year`) are wire values.

`_viewForState` still owns the loading > error > empty > list precedence; it now takes `readonly unknown[]` because it only ever read `.length`, and the active chip supplies the count.

**The cache topology changed with it.** `libraryKeys.home` is gone. The tracks family is an `InfiniteData<ListTracksResponse>` under the `['library','tracks']` prefix, so `trackCachePatch` walks pages and patches every cached variant through `setQueriesData` — a query-keyed cache means there is no longer one snapshot to write. `libraryKeys.lookup` is a separate flat family for detail's narrow "tracks matching this album/artist" reads. Albums and Artists are aggregates: a track-level event cannot be patched into them, so add/delete **invalidate** those two families instead.

Playlists are still sorted on the device. They are a small list the client already holds in full, with no server sort to defer to, and inventing one would be a query for a dozen rows.

## Behaviour parity after the server migration (2026-07-25)

Two things the migration changed by accident, and how they were put back:

**The Tracks count.** `SortControl` renders "N tracks", and with a paged list the loaded array length is the page size, not the library. It reads `tracksState.total` — the server's count — and falls back to 0 only when nothing loaded, so a filtered-to-nothing view still reads "0 tracks" and triggers `LibraryNoResults`.

**The empty-library CTA.** It used to key off the always-loaded track list, so it could show on any chip. With per-chip queries there is no such list, and the CTA collapsed to the Playlists chip only. `useLibraryIsEmpty` restores it: a `limit: 1` probe reading `total === 0`.

That probe sits under `libraryKeys.summary`, deliberately **outside** the `['library','tracks']` prefix. The patchers sweep that prefix expecting `InfiniteData`, and a flat `ListTracksResponse` parked under it would blow up `mapPages` on the first acquisition event. It is invalidated with the album and artist lenses instead, since like them it is derived from the whole collection rather than from one row.

## Re-acquire audio (2026-07-26)

`buildTrackMenuItems` gained a **Re-acquire audio** entry, shown only for ready tracks and only when the screen supplies `onReacquire`. It is deliberately worded away from "download": in this menu `Download` / `Remove download` already mean *offline pinning*, which is a different concept from replacing the acquired master. The action answers "this is the wrong recording — a music video, a remix — get me another one" without the delete/search/re-add loop.

`useReacquireTrack` posts to `/v1/tracks/{id}/reacquire` and patches the track to `pending` **on success only**, unlike `useRetryAcquisition` which patches optimistically in `onMutate`. The difference matters: a retry starts from a failed track that has nothing to lose, while a re-acquire starts from a track that is playing fine, so showing it as pending before the server has accepted would misreport a working track. On error it says so explicitly — the current audio is unchanged — because that is the server's actual guarantee. Wired into `LibraryScreen`, `PlaylistDetailScreen` and `FeaturingScreen`, the three screens that already build the track menu.

**Query results are destructured, never spread (2026-07-30).** TanStack Query v5 tracks which result fields a component reads, via getters, and re-renders only when one of those changes. Spreading the result — `return { ...infinite, data }` — touches every getter, so the subscription widens to the whole object and any field changing re-renders the consumer. react-doctor flags this as `query-destructure-result`, and it was one of only two error-severity findings in the app. Both hooks now destructure exactly the fields they re-export.

## Selection mode and bulk actions (2026-08-01, issues #20 / #22)

Three separate reports asked for the same missing primitive. #18 wanted a discovery result to reach a playlist without the save → three-dots → add dance; #20 wanted a playlist to be fillable from the library, "in bulk instead of one by one because playlists grow fast"; #22 generalised that to acting on many tracks at once. Building #20's picker as a bespoke multi-select modal and then adding a library selection mode later would have produced two selection implementations, so one primitive backs all three.

`useSelection` holds `readonly string[] | null` — `null` *is* "not selecting", so activeness is not a second boolean that can disagree with the array. `toggle` on the last selected id returns `null` rather than `[]`, so deselecting everything leaves selection mode the way a user expects, and `toggle` on a fresh hook enters it, so a row press can never select into a null set. `begin` is idempotent on an active selection: a long-press on an already-selecting list must not wipe what is chosen. `selectAll([])` deliberately does *not* exit — it is an explicit "deselect all" from the bar, and dropping out of selection mode there would be a different gesture than the one pressed. `ids` is a copy, so a caller mapping over it cannot write back into the hook's state.

`LibraryRow` takes an optional `selectable` and an optional `onLongPress`. When `selectable` is present the row's press toggles instead of playing, the trailing cluster (offline badge, duration, the more button) is replaced by a checkbox, and `accessibilityRole` becomes `checkbox` with a `checked` state — a row that behaves like a checkbox must announce itself as one. Both new props are in the `memo` comparator; without them a long list stops re-rendering its checkmarks.

Which actions appear is per surface, because the destructive one differs: the library tracks list removes from the library, playlist detail removes from the playlist. The other three (add to playlist, download/remove download, add to queue) are shared. Download and queue are disabled unless the selection contains a ready track — offering "Download" on a selection of pending tracks would be a no-op that looks like a failure. Both destructive actions confirm first and name the count.

That "three shared, one per-surface" shape is why `buildSelectionActions` exists rather than an array literal in each screen. The first cut had both, and fallow found them as a clone family — 58 duplicated lines whose only real difference was the danger entry. The helper mirrors `buildTrackMenuItems`: the screen passes its selected tracks, the pinned-store handles, and its own `danger: {label, onPress}`, and gets the assembled list back. Two copies of "is every ready track pinned?" would have been two places for the Download/Remove-download label to go wrong.

Bulk add, bulk remove-from-playlist, download and queue are each one call. Bulk delete-from-library is the exception: there is no batch delete endpoint, so `useDeleteTracks` loops the single-track one and reports how many of the requested tracks it actually removed. Track deletion has audio-store side effects, and a server-side batch for it is a larger change than these issues warranted; the partial-result report is what keeps the loop honest rather than silently half-succeeding.

`AddTracksToPlaylistModal` is #20's entry point, reachable from the hero's `+`, the overflow menu and the empty state. It reuses `useLibraryTracks` and `useLibrarySearch` rather than a bespoke fetch, so search and paging behave the same as the Tracks chip. Tracks already in the playlist render as a flat disabled row labelled "Added" instead of being filtered out — a user who searches for a track they added last week should be told it is already there, not shown an empty result.

Selection mode is offered on track lists only. Bulk on an album is just "the album", and album detail already has save-all; adding checkboxes to the Albums and Artists grids would be a second selection vocabulary for a gesture nobody asked for.
