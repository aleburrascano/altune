Renders the detail screen for a tapped discovery result. It is fed entirely by an in-memory handoff (`@shared/lib/detail-handoff`, written by [discover-feature](discover-feature.md)) — there is no per-item backend fetch on open; an empty handoff (cold start/reload/deep link) redirects to `/discover`. `ui/DetailScreen.tsx` no longer draws anything: it resolves the handoff, computes the banner's title and secondary line, and dispatches to one per-kind body (`TrackDetailBody`/`AlbumDetailBody`/`ArtistDetailBody`). Each body renders `ui/DetailScaffold.tsx`, which owns the single vertical scroll and its shape — see [Screen shape](#screen-shape-detail-screens-rework-2026-07-26). There are no tabs, no always-on provider slabs, and no genre pills. Content loads with shape-matched skeletons (`ui/DetailSkeleton.tsx` — `TrackRowsSkeleton` for the album tracklist and artist top-tracks, `AlbumCardsSkeleton` for the discography sections), the same idiom discover/library use, rather than a bare centered spinner; the only remaining `ActivityIndicator` is the labelled inline "Searching…" feedback for a lateral-nav hop.

**Library enrichment (non-destructive)**: library items reach the screen with no `sources` (saved rows store none), so `hooks/useEnrichResult.ts` back-fills them via a discovery search to make the item playable and its tracklist/discography fetchable. The match requires title AND (when known) artist to agree — never title alone, and with no fuzzy fallback — and the merge spreads the stored result last so the library's own `extras` win on every conflict: enrichment may only *add* `sources` plus provider-only keys (mbid, preview_url), never overwrite the album/artist. This fixed the "Green Day by Che" bug where a loose title-only match swapped the real album out from under the user.

**Provider enrichment**: `hooks/useDetailEnrichments.ts` is the single seam deciding which of the three rendered provider hooks (MusicBrainz `useEnrichment` — the header year, all kinds; Deezer — `featured_artists`, track+album; Last.fm — the artist About, artist only) fire for a given `kind`, expressed via each hook's `enabled` flag rather than conditional hook calls (React's rules of hooks). Each provider hook is built on the shared `useEnrichmentQuery` skeleton (Template Method, function-value form) — one `useQuery` with a 24h `staleTime`, gated by a `hasContent` predicate so an unresolved/empty payload collapses to `null` and its section hides. This mirrors the backend's own [enrichment](../backend/discovery/enrichment.md) subsystem. The retired surface was **deleted, not left dark** (2026-07-16 structure audit F1): the Discogs album/artist and lyrics hooks used to fire real fetches for sections that were never rendered post-declutter, and `DiscogsEnrichmentSection`/`DeezerEnrichmentSection`/`DiscogsArtistSection`/`LyricsSection`/`EnrichmentSection` plus their api-client functions are gone (git history keeps them; lyrics belong to the full player when it lands). The surviving detail-open client surface — catalog browse (`getAlbumTracks`/`getArtistTopTracks`/`getArtistAlbums`/`getRelatedTracks`) and the MusicBrainz/Last.fm/Deezer enrichment functions — imports from `@shared/api-client/enrichment`, split out of `discovery.ts` so detail-only growth never churns the module discover depends on (2026-07-17 discover structure audit F1; see [shared-api-client](shared-api-client.md)). The artist About renders only `LastFmEnrichmentSection` — bio (with Read more) → similar-artist rows — gated on `enrichments.lastfm !== null`. Its other two payload fields are consumed elsewhere on the same screen rather than repeated inside About: `tags` become the banner's secondary line (at most two, `·`-joined) and `listeners` becomes the `Listeners` fact cell. This is why the section no longer renders a `listeners · plays` line or genre chips — the pills made a genre and an artist name look identical, so similar artists became rows with an avatar and a chevron.

**Play**: the track action is the scaffold's primary pill (`ui/DetailActions.tsx`), labelled `Play` / `Play preview` / `Pause` with a haptic. It plays the full Track when in the library (effective id/acquisition status resolved from `extras` OR the live library match — the pure `resolvePlaySource` in `play-source.ts`, unit-tested without rendering), else the 30s Deezer preview, else it is disabled — testIDs `detail-play` (library source) / `detail-preview`. Which of the two is in play is stated by the `Source` fact cell (`Preview` in warning tone, else `Library`), not by a caption under the button: the old amber "30-second preview" banner was one-off furniture for information the fact row already had a slot for. Every play is stamped with the handoff's `search_id` and the result's `result_signature` so play/completed events join back to the originating search (the behavioral corpus). Album/artist hero Play is intentionally deferred: their tracklists are discovery results and `buildPlayableQueue` only queues `ready` Tracks, so it would have nothing to play. Featured artists are structured `{name, mbid, deezer_id}` credits (`FeaturedArtist`, parsed by `@shared/lib/featured`'s `featuredArtistsFromExtras`, which tolerates legacy bare-name strings), populated by the backend's FeaturedArtistResolver; the track body's three-tier fallback (structured extras → Deezer enrichment contributors → regex-parsed "feat./ft./with" from title/subtitle) is the pure `resolveFeatured` in `extras.ts`, unit-tested without rendering. The Featuring row navigates to the current tab's `/featuring` browse route carrying the mbid/deezer_id params.

**Save-to-library**: `hooks/useSaveTrack.ts` is a TanStack Query mutation with an optimistic lifecycle over the library snapshot (`libraryKeys.home` from `@shared/lib/query-keys`; the retired `['library']` infinite cache was dropped from the flow by the 2026-07-16 library structure audit) — `onMutate` prepends a pending placeholder (the detail save control and Activity Dock read library-home), `onSuccess` swaps the placeholder for the real server row (`replaceOptimisticTrackHome`) so acquisition SSE events — which carry the real id — match it, deduping by id when the SSE upserted the row first, `onError` rolls back the snapshot, `onSettled` invalidates so a dedup hit reconciles. All transforms are pure in `save-cache.ts`. Invariant: the insert helper never seeds an absent cache — `undefined` means errored/not-fetched, NOT empty (`{items: []}` is the empty library); seeding used to fabricate a one-track library over a 401 error state that `staleTime: Infinity` then pinned for the session (a 273-Track library rendered as one Track/album/artist). The hero save is an outline pill in `TrackDetailBody` (testID `detail-save`) running the acquire lifecycle add → saving → ready/failed from `save-control-state.ts` over the reactive library match, disabled with no POST when the Track has no artist; `TrackSaveControl` remains the 40pt circular row control on album/artist tracklists. The lifecycle's presentation vocabulary is shared, not duplicated: `saveControlLabel`/`saveControlText` live beside the state machine in `save-control-state.ts` and the state→glyph mapping is the single `ui/SaveGlyph.tsx` (the two controls differ only in their `add` glyph props). Reactivity: `hooks/useLibraryTrackMatch.ts` subscribes to the library-home query via a `skipToken` observer (it never fetches, only observes) so an acquisition-SSE `setQueryData` patch re-renders the save control and PlayButton without a library-wide invalidate; the pure lookup `findTrackInData` was split out of the imperative `helpers/find-track-in-library-cache.ts` wrapper for it, and `useIsTrackSaved` is a thin boolean reader. On success the mutation still enqueues a `library_add` telemetry event via the critical outbox (see [shared-telemetry](shared-telemetry.md)), carrying the originating `search_id`. It **omits** `result_signature` when the handoff has none rather than sending `null`, and so does `useReportWrongAlbum`'s `wrong_album`: Go's `validatePayloadTypes` 400s a present-but-non-string value, and because these two events take the durable tier, a rejected entry used to sit at the head of the outbox and block every label queued behind it.

**Track numbers (derive-then-persist, three layers)**: (1) `toCreateTrackRequest` (`save-cache.ts`) maps `extras.track_position` → `CreateTrackRequest.track_number` (and forwards `featured_artists`), so new album-context saves store the real position. (2) For Tracks saved before that (stored `track_number` null), `_withAlbumPositions` in `hooks/useAlbumDetailState.ts` recovers album order at view time by matching each owned Track against the eagerly-fetched authoritative provider tracklist (provider order IS the album order); a stored position always wins, unmatched Tracks sink to the end, and the derivation is display-only and re-derived per view so it never goes stale. (3) `hooks/usePersistTrackNumbers.ts` fire-and-forgets a `PATCH /v1/tracks/{id}/track-number` per derived position — deduped per screen by a ref, skipping optimistic placeholders — so the database self-heals as albums are browsed; the server write is fill-only (`WHERE track_number IS NULL`), hence idempotent and unable to clobber a real value. The same eager tracklist fetch gates the "More from this album" expander (`detail-more-from-album` hides for singles/fully-owned albums instead of dead-ending) and holds a library album's list until the order is known, so positions are correct on first paint.

**Navigation seams (2026-07-16 structure audit F2/F3)**: `navigation.ts` owns the typed route vocabulary (`TabRoot`/`DetailRoute`, `tabRootFromSegments`, `detailRouteFor`, `featuringRouteFor`) and `openDetail(router, detailRoute, result)` — the only sanctioned way to open a detail screen, pairing the handoff write with the push so the "never push without a handoff" invariant is single-sited (all five former `setDetailHandoff`+`push` call sites route through it). `resolve-entity-query.ts` is the one cache identity for "resolve an entity by name" — a `queryOptions` factory (`['resolve-entity', kind, q, limit]`, 30min staleTime) shared by `useLateralNav` (via `queryClient.fetchQuery`, `retry: false` to keep its fail-fast behavior), `useArtistDiscovery`, `useAlbumDiscovery`, and `useEnrichResult` (limit 5) — so a lateral hop no longer hits the backend twice for the same lookup.

**Lateral navigation**: `useLateralNav` resolves by name through the shared resolve-entity cache and pushes a fresh detail screen for tapped artist/album names, guarded against duplicate pushes. Album/artist content (`useAlbumTracks`, `useArtistContent`) fetches from provider APIs directly (not the handoff), merging MusicBrainz and Deezer sources with an MB-authoritative filter when identity is verified. Both the top-tracks and albums fetches thread `artistName` to the backend so its identity fan-out can name-resolve providers MusicBrainz never bridges (SoundCloud) and surface an SC-exclusive artist's tracks/albums (see [soundcloud](../providers/soundcloud.md)). A library artist's "Your Tracks" list is capped at 5 with a `detail-show-all-tracks` reveal so the discography isn't buried.

Key files: `hooks/useDetailEnrichments.ts`, `hooks/useEnrichmentQuery.ts`, `hooks/useEnrichResult.ts`, `hooks/useSaveTrack.ts`, `hooks/useLibraryTrackMatch.ts`, `hooks/useAlbumDetailState.ts`, `hooks/usePersistTrackNumbers.ts`, `ui/DetailScreen.tsx`, `ui/DetailScaffold.tsx`, `ui/DetailActions.tsx`, `ui/DetailFacts.tsx`, `ui/Section.tsx`, `ui/TrackDetailBody.tsx`, `ui/ArtistDetailBody.tsx`, `ui/AlbumDetailBody.tsx`, `navigation.ts`, `resolve-entity-query.ts`, `play-source.ts`, `save-cache.ts`, `save-control-state.ts`, `helpers/find-track-in-library-cache.ts`.

## Hero Play on album and artist (2026-07-24)

The mockups always had one; it was deferred because album/artist tracklists are *discovery results* with no audio behind them, and `buildPlayableQueue` filters a queue to `acquisition_status === 'ready'`. A naive Play on an album you own none of queues nothing and reads as broken. The product decision (2026-07-24) is **play what you own, offer the rest**.

`owned-playback.ts` holds the rule, shared by both bodies so they cannot drift. `splitOwned` resolves the *displayed* list against the library cache — display order, so the queue plays in album order rather than whatever order the library happens to hold — and returns three groups:

- **playable** — owned and acquired; the queue Play starts
- **unownedCount** — nothing in the library yet; what "Save N" offers
- **acquiringCount** — saved but `pending`/`failed`; neither playable nor worth re-saving

Keeping `acquiring` separate is load-bearing: folding it into `unowned` offers to re-save something already queued, and folding it into `playable` promises audio that does not exist yet. It no longer surfaces on screen at all: `detail-screens-rework` cut both the "N still downloading" caption and the saved/downloading progress bar the mockups tried, because a per-album completion readout framed owning music as a checklist. The split still drives the two buttons' labels and disabled states; per-track state stays on each row.

`playButtonState` names the count (`Play 3`) whenever the list is only partly playable — a bare "Play" over 3 of 12 tracks reads as a bug when the queue ends early. With nothing playable, Play is disabled and Save takes the primary variant, so the button that actually does something is always the prominent one. Artist detail hides the control entirely while its track section is loading or empty rather than showing a disabled button over nothing.

TestIDs: `detail-album-play`, `detail-artist-play`. `detail-save-all` labels itself `Save N` and renders only when something is unowned. `detail-album-acquiring` is gone with the caption it named.

## Screen shape (detail-screens-rework, 2026-07-26)

The three kinds used to be one route with three drifted layouts: track stacked Play and Save centred, album put them side by side, artist used a full-width button; album's own `2013 · 8 tracks · 48 min` line rendered *below* its tracklist; and a bare back chevron over a 200pt centred hero meant scrolling cost you all context. `ui/DetailScaffold.tsx` is the fix — the drift was the bug, so consistency is now structural rather than a convention to remember. Top to bottom it owns:

1. **Floating app bar** — translucent circular back and ⋯ over the artwork. It crossfades to an opaque `canvas` bar with the object's title once the banner scrolls past (`Animated.ScrollView` + one native-driver `interpolate`, so nothing runs on the JS thread per frame). That bar title is `accessibilityElementsHidden` — it is a visual duplicate of the banner title and would otherwise be announced twice.
2. **Banner** — the artwork, cover-cropped, full-bleed, 318pt, running to `y=0` behind the status bar under a five-stop gradient scrim to `canvas`. It carries **identity only**: the title at the `editorial` type step (34/38, `-1` tracking, clamped to 2 lines) and one secondary line — the tappable lateral-nav artist link for track and album, the genre line for artist. Nothing else sits on artwork we do not control; facts and controls stay on canvas where their contrast is ours to set. That was the deciding constraint against the mockups that put the fact cells or Play itself on the scrim.
3. **Action row** — full width. The primary pill `flex: 1`-grows and secondary controls trail it, so the row ends exactly on the right margin instead of leaving the gap the centred layout had.
4. **Fact row** (`ui/DetailFacts.tsx`) — up to three `overline` label / `bodyStrong` value cells at `space-between`, under a hairline. **Only intrinsic facts belong here**; an absent value omits its cell rather than rendering blank. Track gets `Length · Released · Source`, album `Tracks · Runtime · Released` (moved up from below the tracklist, where it described a title 8 rows away), artist `Releases · In library · Listeners`.
5. **Sections** (`ui/Section.tsx`) — one uppercase label with an optional accent action, replacing four different heading styles. Artist's `About` is a plain section now, not a `Disclosure`; that component is deleted, having had one consumer.

**Discography is one rail, not three.** `DiscographySections` used to stack a titled rail per record type — Albums, then Singles, then EPs — which cost three headers and three rows of vertical space to show three lists you look at one at a time. It now renders a **filter-chip row over a single rail**: one chip per record type present, each carrying its count, switching which list the rail shows. The chips are suppressed entirely when only one type exists, so an artist with nothing but albums gets no pointless single chip. Expanding past the 10-item cap resets when you switch chips, since "see all" belongs to the list you were looking at.

**Ownership updates live.** The save control and the `Source` fact no longer need a screen exit to catch up: `useOwnedTrack` takes the result's `{title, artist}` and resolves a track id from the `trackStatusStore` identity index when the result carries no server stamp, then subscribes to the status under it. Tapping Save flips the control to *Saving…* immediately (the optimistic id is linked in `onMutate`) and to *Saved* when the acquisition SSE reports ready, at which point `resolvePlaySource` starts returning the library source and the fact cell flips `Preview` → `Library`. `TrackSaveControl` does the same resolution per row, so album and artist tracklists stay live too — it is a component, which the artist rows' `.map()` callback is not, so that is where the subscription has to live. See [shared-acquisition](shared-acquisition.md#the-identity-index-2026-07-26).

Two things left the body rather than being restyled. The album name is no longer in a track's fact line: it was already a `Details` row with artwork and a chevron, so the meta line was duplicating the one place it is actually tappable — and that duplication is what made the line read as a run-on. `Wrong album?` moved into the ⋯ menu, being a report action rather than content; the menu hides entirely when it has no items, which is why album and artist show no ⋯ today.

The `editorial` and `overline` type steps and the `space-between` fact row are load-bearing against short titles: `Get Lucky` at the old `displayL` trailed off across a 328pt banner, and three dot-separated facts left the right half of the row empty. Bigger type and edge-anchored cells are what fill the width.

The retired enrichment surface was deleted rather than left dark (2026-07-16 structure audit): the unrendered `Discogs*`, `Deezer`, `Lyrics` and `EnrichmentSection` components, their hooks and their api-client functions were firing fetches nobody rendered. `useDetailEnrichments` composes exactly the three rendered providers — MusicBrainz for the banner year on all kinds, Deezer for `featured_artists` on track and album, Last.fm for the artist banner genres, `Listeners` fact and About.

## Lifecycle and cache behavior

`saveControlState` derives the add → saving → ready → failed lifecycle from the library React Query cache, and `saveControlLabel` plus `SaveGlyph` are shared between the hero save pill and the per-row `TrackSaveControl` so the lifecycle vocabulary cannot drift. It advances on query invalidation today; the `/v1/events` SSE `track_acquired` event makes it instant.

`useSaveTrack` prepends a pending placeholder to the `libraryKeys.home` snapshot on mutate, rolls back to that snapshot on error, and invalidates on settle so a dedup hit reconciles to the server row. The placeholder includes null values for the extended metadata fields added by the `import-legacy-library` spec.

`useEnrichResult` back-fills `sources` for a library item — saved rows store none — so it becomes playable and can fetch tracklists. It matches on title **and** artist, never title alone, and merges so the stored library `extras` always win: enrichment may only add `sources` and provider-only keys. A loose title-only match previously clobbered the real album, which is the "Green Day by Che swapped the album" bug.

`useLateralNav` resolves artist and album by name through the shared `resolve-entity-query.ts` cache, which `useArtistDiscovery`, `useAlbumDiscovery` and `useEnrichResult` also use, so the landed screen reuses the hop's fetch. Its `searchingRef` guard never resets after a successful push, which is what prevents duplicate detail screens; the new screen gets its own fresh instance.

`useArtistContent` unions MusicBrainz and Deezer albums via `dedupAlbumsByTitle` (normalized key, keep highest `track_count`, merge sources), sorted by release date descending. When the identity is verified and MB returned a non-empty list, Deezer may only enrich title-matched albums and contributes no new titles — Deezer's artist entities conflate same-name artists, and its album entries carry no artist field to filter on. Unverified artists keep the full union. Provider failures arrive as HTTP 200 with `status: 'timeout'`/`'error'` and empty items, so the hook treats any non-ok payload as that provider's failure and `isErrorAlbums` fires only when every available provider failed.

Track numbers work in three layers. `toCreateTrackRequest` maps `extras.track_position` to `CreateTrackRequest.track_number` so new album-context saves store the real position. For tracks saved before that, `_withAlbumPositions` recovers order at view time by matching owned tracks against the authoritative tracklist — display-only and re-derived per view, so it can never go stale, and a stored position always wins. `usePersistTrackNumbers` then fire-and-forgets a `PATCH` per derived position so the database self-heals as albums are browsed; the server side is fill-only and therefore idempotent.

## Ownership comes stamped (2026-07-25)

"Is this result already in my library?" used to be answered by `findTrackInData` — normalized title+artist matching against the whole library snapshot, feeding `saveControlState`, `splitOwned`, `resolvePlaySource` and the album/artist Play buttons. That is the single reason the detail screen needed the entire library resident.

The server now stamps every track result with `extras.owned_track_id` and `extras.owned_acquisition_status` (see [discovery](../backend/discovery/index.md)). `trackExtras` reads them as fallbacks for the existing `track_id` / `acquisition_status` keys, so `resolvePlaySource` picked it up with no change to its rule. `hooks/useOwnedTrack.ts` is the reactive read: the stamp is the value at fetch time, overlaid with anything newer from `@shared/acquisition/trackStatusStore`, which the SSE router writes on every acquisition event. That store is what replaced the query-cache observer — the save control still flips the instant a download finishes, without the library being in memory.

`splitOwned` now takes only the displayed results and pairs each playable with the result it came from, so `toPlaybackQueue` can build the queue without a second lookup; `saveStateFor` takes a result rather than a title/subtitle pair.

`helpers/find-track-in-library-cache.ts` and `hooks/useLibraryTrackMatch.ts` are gone. `hooks/useLibraryTracks.ts` survives for the library-origin album and artist views, but it now asks the server (`GET /v1/tracks?q=`) and filters the small result set precisely, rather than scanning everything.

## Artist content in one call, positions filled by the server (2026-07-25)

`useArtistContent` was three parallel per-provider queries plus `helpers/artist-content.ts` (dedupe by normalized title, merge source lists, back-fill artwork, sort by release date) and `helpers/normalize-for-dedup.ts` (a 30-line normalizer). It is now one `getArtistContent` call; all four of those files are deleted. `useAlbumTracks` likewise dropped its second MusicBrainz query and `_mergeFeaturing` — it passes `mbid` and the server merges.

`usePersistTrackNumbers` is gone. The server fills a missing `track_number` from the provider tracklist's own order when the album is fetched, so the database still self-heals as albums are browsed, without one `PATCH` per track leaving the phone.

`useSaveTrack` keeps its optimistic placeholder — instant feedback is a client concern — but it now inserts into the paged tracks cache via `upsertTrackInCaches` and swaps in the real row with `replaceTrackInCaches`. The old "never seed an absent cache" invariant survives in those helpers: both no-op when nothing is cached.
