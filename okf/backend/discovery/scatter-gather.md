`Service` (search.go) is the orchestrator for discovery's rebuilt pipeline: Layer 0 query cleanup → Layer 1 fan-out → Layer 2 merge → Layer 3 rank, plus orthogonal concerns (artist-dedup, disambiguation, artwork, correction, related groups, telemetry, vocabulary learning). `Service.Execute` is the entry point: it cleans the query (`CleanQuery`, see [query-correction](query-correction.md)), normalizes it (`textnorm.NormalizeForMatch`), mints a `searchId` (the keystone joining downstream engagement events, see [telemetry](telemetry.md)), checks the app-wide `resultCache` (query+kinds keyed, TTL'd, only cached when complete and non-empty; since 2026-07-23 also bypassed entirely when the query normalizes to `""` — symbol-only queries like "!!!" and "†††" previously collided on one degenerate key — and never written when a correction fired, so corrected results can't be served under the typo key without their `CorrectedQuery` provenance), and on a miss calls `fanOut` then `mergeRankEnrich`.

`fanOut` queries every `ports.SearchProvider` concurrently, each bounded by `defaultProviderTimeout` (1500ms, overridable per-provider via an optional `SearchTimeout()` method) and gated by a `CircuitBreaker`. Each goroutine writes only its own slot in a fixed-size, provider-ordered slice — never goroutine-completion order — so downstream ranking of tied results is deterministic run-to-run. Hardening (2026-07-23): each provider goroutine recovers panics (one bad third-party payload degrades that slot instead of killing the process); a provider error is NOT counted against the breaker when the *parent* request context was canceled (client-abandoned searches previously marked every provider failed at once, opening all breakers app-wide); the half-open breaker admits exactly one probe. Results collapse to `perProvider [][]domain.SearchResult` (only non-empty groups) plus per-provider `ProviderSearchResponse` statuses for the wire.

`mergeRankEnrich` is the decision core: `stampIdentities` (cache-only read of the `IdentityBridge`, setting `SearchResult.Xref` on MB-sourced results so Merge can resolve identity across providers — see [identity-artwork](identity-artwork.md)) runs pre-merge, then persists each learned bridge off the request path (`launchBackground`); when `IDENTITY_VERIFY_ON_PERSIST` is on, an `IdentityVerifier` (`identity_verify.go`) first drops any streaming edge (deezer/spotify/apple) whose provider catalogue doesn't overlap the artist's MusicBrainz release-groups — a mis-bridged same-name artist from a wrong MB url-relation (the permanent counterpart to the detail-time MB anchor: same `groupMatchesAnchor` overlap test, moved upstream and applied per edge, memoized per MBID). `VerifyXref` returns `(xref, ok)`: a memo hit returns `ok=false` and the caller **skips the persist** — the memo previously returned the caller's raw xref, so every repeat search within the memo TTL upserted the unverified edge back over the verified row, un-doing the fix (the critical bug of the 2026-07-23 review); a failed `PersistBridges` calls `verifier.Forget(mbid)` so the verified bridge isn't lost for the memo TTL. It filters only the persisted copy, never the in-flight `Xref`, so merge/ranking are unchanged; `pipeline.go`'s `rankPipelineWith` (`Reshape(RankWith(Merge(...)))` — Merge → rank → EnforceDiversity → CollapseArtistDuplicates) is the pure, no-I/O decision core (see [merge-dedup](merge-dedup.md) and [ranking](ranking.md)); then every result's `Signature` is stamped (pre-disambiguation, the byte-stable behavioral join key — see [telemetry](telemetry.md)) and `applyArtistDisambiguation` and `fillArtwork` fill fields without reordering. Zero results triggers `tryCorrection` (re-fanout on a corrected query, which now returns the corrected run's provider statuses so the wire envelope is honest about what actually served). Since structure-audit F1 (2026-07-16) the experiment inputs cross the package boundary as the exported `RankOptions` (TailDemotion / CrossKindProminence / Behavioral), mapped onto the internal `rankConfig` at a single site (`RankOptions.config`) — `RankWith` and `Reshape` are exported so the Mission Control re-run composes the identical flag-gated stages instead of a zero-value config; `Service.BehavioralScoresSnapshot` is exported for the same reason. `pipeline.go` also exposes `rankPipeline` (zero-value options — the sacred-test default) and `rankPipelineNoReshape` (skips the diversity/collapse tier, the eval baseline for `cmd/discoveryeval -mode diversity`), plus `RankExplain`/`ScoredResult` — a rank that returns each result paired with its scoring provenance instead of discarding it, routed through the same `rankScored` core as `RankWith` (see [ranking](ranking.md)) so the Mission Control re-run's rank explainer can't diverge from production order.

**Paging (2026-07-24).** `Execute` builds the full ranked slate and truncates *last*, which is what makes `SearchQuery.Offset` a pure slice rather than a re-query: the `resultCache` value is deliberately the whole pre-limit list (see `resultCacheKey`), so page N of a query is a window onto the same cached list page 1 came from — no provider re-fan-out, and ordering is stable across pages for the cache's lifetime. `pageOf(ranked, offset, limit)` returns an empty page for an offset past the end rather than erroring, because the slate shrinks when a provider drops out and a client holding an offset from a larger slate must degrade, not fail. `SearchOutput` carries `Total` (slate size before paging), `Offset` and `HasMore`. `domain.NewPagedSearchQuery` validates the offset against `domain.MaxSearchOffset` (200).

Three side effects are **page-1 only**, guarded on `query.Offset == 0`: `persistHistory`, `emitSearchEvent` and `ingestVocabulary` all describe the *search*, not the page, so scrolling must not log a second search, re-ingest the same slate, or emit impressions whose positions restart at zero. Exploration (`maybeExplore`) is page-1 only for a different reason — shuffling a later page would reorder it independently of the pages already on screen, so the user would see repeats and gaps, and exploration exists to perturb what is seen *first*.

The four ranking-pipeline experiment flags (`tailDemotion`, `crossKindProminence`, `behavioral`, `exploration`) live on an embedded `rankingExperiments` struct rather than as direct `Service` fields — grouped so "what experiments exist on this Service" is one type to read instead of fields scattered across the struct, while embedding (rather than a named sub-field) keeps every existing `s.tailDemotion`-shaped access unchanged. Optional dependencies are wired via functional options (`WithHistoryRepository`, `WithVocabularyStore`, `WithArtworkResolver`, `WithIdentityBridge`, `WithIdentityStore`, `WithIdentityVerifier`, `WithResultCache`, `WithTailDemotion`, `WithCrossKindProminence`, `WithBehavioralRanking`, `WithExploration`) — each is a no-op/inert path when absent, so the composition root (`internal/app/app.go`) toggles experiments without touching `Service` internals. `Service.bgWg` (a `sync.WaitGroup`) tracks best-effort background work (identity-bridge persistence, vocabulary ingest); `WaitForBackground` blocks until it drains, used by graceful shutdown and tests. The `launchBackground` helper centralizes the fire-and-forget goroutine pattern — detach the context from request cancellation, `bgWg.Add`, and defer both `bgWg.Done` and a recover+log so a panic in background work can't crash the process — and is used by `stampIdentities`'s identity-bridge-persist goroutine.

A panicking provider adapter must not kill the process — the fan-out records the panic and continues — and each goroutine writes only its own slot, so output follows the fixed provider order rather than completion order. The durable identity persist runs off the request path on a detached, bounded context so it adds no search latency and outlives the request. Exploration shuffles a copy, never the shared cached list, and the organic pre-shuffle top is captured first because vocabulary learning must ingest the organic ranked top. One event is logged per search, not per page.

The exported `Merge` / `RankWith` / `Reshape` composition lives outside `Service` so the Mission Control re-run ranks with the same core production does and can never diverge; `RankExplain` keeps each result's scoring math and is a pure read for the re-run inspector only. Display-enrichment stages stay on `Service.mergeRankEnrich` — they fill fields, they do not decide order. The engagement-join signature is computed before disambiguation fills fields, because a signature computed after would flap between searches and never rejoin.

## The slate rides along with the page (2026-07-25)

`SearchOutput` gained `Slate`, built between paging and the return. The order matters: `pageOf` truncates `ranked` to the requested window, but the pre-truncation list is kept as `fullSlate` so the blended sections can be grouped over everything the search found rather than over one page. `maybeExplore` then runs on the page, and the slate is built from *both* — page first (its head is the top result the user sees) and full list (its groups are the sections).

The slate is only built when `Offset == 0`, alongside history persistence and the `search_performed` event. Later pages carry a zero-value slate, which is what the client expects: it reads sections from page 1 exactly as it reads `search_id` and corrections.
