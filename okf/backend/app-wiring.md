`internal/app` is the composition root: the only place adapters are chosen and injected into ports, per the project rule that the object graph is wired explicitly. `App` (`app.go`) owns config, the pgx pool, the (nilable) Redis client, the HTTP server, and every lifecycle-bound background component (acquisition scheduler, vocab refresh, event bus/feed, alert monitor, log ring, provider health, eval meter). `setup(ctx)` (~30 lines since structure-audit F5, 2026-07-16) assembles in order: pools → auth verifier → event bus → `wireDiscovery` (content/consensus, search service, background tickers, enrichment, handler, vocab refresh) → `wireCatalog` (catalog+acquisition; needs discovery's featured bridge, hence the order) → `wirePlayback` → `mountRoutes` → `wireAdmin` (Mission Control, including `WithMetricsHistory(discoveryPersistence.NewPgxMetricsRollup(a.pool))` for the durable rollup trend panel) → alert monitor; each stage method owns one context's construction and the values crossing contexts travel explicitly through the small `discoveryWiring`/`catalogWiring` structs. `wireDiscovery` itself (`discovery_wiring.go`, split out of `app.go` per structure-audit F1, 2026-07-18) delegates to three sub-stage methods in sequence — `wireDiscoveryConsensus` (the multi-provider album consensus service), `wireDiscoveryContent` (featured-artist bridge + album/artist/related/suggest services, consensus-fed — the album-tracks service resolves native tracklists from Deezer, iTunes, Apple Music, Spotify, and SoundCloud (one shared SoundCloud adapter instance backs the album/artist/related content maps), and any other-sourced album falls back to an artist-guarded Deezer title search), `wireDiscoveryEnrichment` (the MusicBrainz detail-open enrichment service, nil when MB isn't configured) — mirroring the extraction `search_wiring.go` already applied to the search pipeline; each sub-stage returns a small struct or single value, no new interfaces. Event publishers (catalog/acquisition services) receive the bus wrapped in admin's `eventtap.Tap` decorator — the Mission Control system-wide tap — while the per-user SSE handler subscribes to the inner bus directly; the acquisition wiring also hands the acquire service the id3 tagger adapter (`WithAudioTagger`) and gives the scheduler its own tap reference for per-job progress events (`WithSchedulerEvents`) instead of the reporter reaching through the service; the database is *not* nil-tolerant: `database.NewPool` errors on an empty `DATABASE_URL`, so a misconfigured process fails at startup instead of panicking per request. **Nil-tolerant degradation pervades**: nil Redis, nil MusicBrainz, nil audio store, nil enrichment all switch features off rather than fail — e.g. without an audio store the acquisition scheduler is nil and the retry endpoint isn't mounted. Playback's `NowPlayingReader` is deliberately *not* in that set: it is built from the always-present catalog `trackRepo` and passed to `NewQueueService` as a required parameter, so a miswired graph fails at construction instead of silently dropping `current_track` from every resume.

**Detail wiring** (`discovery_wiring.go`): `wireDiscoveryContent` builds the artist-content service over the `artistProviders` map (Deezer, Apple Music, Spotify, SoundCloud, + Last.fm when configured). Apple Music replaces iTunes for artist content — same Apple catalog + ids, but the official Catalog API carries release dates, covers, and ISRC the plain iTunes lookup misses; Spotify joins via its classic `/v1` endpoints with the anonymous web-player token (no persisted-query hash). Each is queried by its bridged id via `providerContentID` (Apple through the shared iTunes id, Last.fm through the MBID) — the "stop excluding them" direction in `docs/brainstorms/2026-07-22-provider-uniform-interface.md`. When a pool exists it also hands that service its own durable `IdentityStore` (`NewRedisIdentityStore(NewPgxIdentityStore(pool), redisClient)` — the same store the search path writes bridges into), and — whenever that store is present — runs the identity-first V2 detail path (the `DETAIL_IDENTITY_FIRST`/`DISCOGRAPHY_V2` flags and their `WithIdentityFirst()`/`WithDiscographyV2()` options were **removed** 2026-07-23; the store's presence is now the sole gate). It reverse-resolves a single `(provider, id)` into the artist's full cross-provider identity and fans discography/top-tracks out by each provider's own id (never a name), so a same-name artist can't bleed in, assembling releases with the rebuilt best-of-merge → confidence-keep → record-type-normalize core (see [merge-dedup](discovery/merge-dedup.md) "Discography V2" and `docs/discovery-detail-pipeline.md` §6); it falls back to the single-provider path whenever the id fan-out comes back empty (or when no store is wired — the unit-test path). The pre-V2 identity path (`identityAlbums`/`identityTopTracks`) was retired at the cutover — the only paths now are V2-identity-first and the single-provider fallback. `WithMBAnchor(sharedMB)` additionally hands V2 the shared MusicBrainz adapter as its identity-verification anchor (`ReleaseGroupTitles`), so a fan-out provider whose catalogue barely overlaps the MBID's release-groups — a mis-bridged same-name artist from a wrong MB url-relation — is dropped (doc §7).

**Search wiring** (`search_wiring.go`): `BuildSearchService` is deliberately the *single construction site* for the search pipeline so the offline eval exercises exactly the ranking users see — the eval CLI, the eval meter, and production all call it. `BuildSearchServiceWithTransport(..., rankingOnly)` adds two seams: an injectable transport (record/replay for fixtures) and `rankingOnly`, which skips display enrichment (artwork chain, related-groups — the bulk of a search's HTTP) and the Redis result cache while keeping every rank-affecting flag live; exploration is *never* wired in rankingOnly so eval order stays deterministic. Eval/synthetic searches always get a nil event store so they never pollute telemetry. Ranking experiment flags: `CROSS_KIND_PROMINENCE_ENABLED` defaults **true** (the only one on by default); `TAIL_DEMOTION`, `EXPLORATION`, `BEHAVIORAL_RANKING`, `EVAL_METER` default false. The durable identity store layers Redis as a read-through front over Postgres (source of truth, survives Redis flushes); `RedisEnrichmentCache` does triple duty as enrichment cache + identity bridge + MBID index, so a detail-open warms the search path. When `IDENTITY_VERIFY_ON_PERSIST` is on, `BuildSearchService` also wires an `IdentityVerifier` (built from the shared MusicBrainz release-group anchor plus deezer/spotify/apple content adapters) so a learned bridge's mis-bridged streaming edges are dropped before the background persist — the permanent identity-fusion fix (see [scatter-gather](discovery/scatter-gather.md)). `BuildSearchServiceWithTransport` takes a pre-built `vocabStore` parameter (falling back to building one from `redisClient` when nil, the offline-tooling path); production passes setup's own instance so **one** vocabulary store now backs both suggest/refresh and search. There remain **two** MusicBrainz adapter instances (one in `wireDiscovery`, one built inside `BuildSearchServiceWithTransport`) — rate safety holds because pacing lives in the shared transport, not the adapter.

**HTTP transport** (`http_client.go`, `live_transport.go`): `defaultLiveTransport` is a package-level `liveTransport` shared process-wide — per-host `rate.Limiter`s (musicbrainz 1/s, itunes 0.5/s, last.fm 5/s, ytmusic 2/s; burst 4 so one query's per-kind fan-out isn't limited against itself) plus retry (3 attempts, 429/5xx, linear backoff). It must stay process-shared: per-client limiters would let N providers each do N× a host's limit — exceeding published limits is what got the prod IP throttled (surfaced as spurious search timeouts). `clientFactory`'s zero value uses the live transport; eval injects record/replay, and replay never touches the live transport. YouTube Music is transport-injected (its library owns a package-global client).

**SSE** (`sse_handler.go`): lives in the composition root deliberately — it is the seam between `shared/events` and the auth context, so `shared/events` never imports auth. Hard-won contracts: never reply 204 to an empty `Last-Event-ID` replay (204 tells EventSource to stop reconnecting — a past hot-loop bug), emit `event: resync` when the ring has evicted events in the requested gap, flush `:ok` immediately, heartbeat every 25s.

**Operator surfaces**: three isolated search stacks exist so failures can't cross-contaminate circuit breakers — production `searchSvc` (breaker inside `NewService`), the eval meter's dedicated `BuildSearchServiceWithTransport(..., rankingOnly)` instance (`eval_runner.go`, off by default; smoke-checks 5 fixed queries against a 0.80 baseline; the meter type itself is `admin/evalmeter.Meter`, its `Runner` implemented here), and Mission Control's re-run (`rerun.go`, builds providers via the exported `BuildDiscoveryProviders` over a recording transport with no Service — bypasses breakers by construction, records per-stage waterfalls via an `ExchangeRecorder`). Since structure-audit F1 (2026-07-16) the re-run ranks with `RankOptions` built from the same config flags production reads plus the live service's `BehavioralScoresSnapshot` — the waterfall runs the identical flag-gated composition, not a zero-value config. It ranks through `discoveryService.RankExplain` (not `RankWith`) so each result's scoring math survives into the response; `projectScored` (`rerun.go`) pairs each `ScoredRow` with its display projection, and `Reshape` still runs over the bare results for the final stage. `search_inspector.go` adapts the *live* service for Mission Control test-search (real pipeline, result cache bypassed, no telemetry). `rerun_detail.go` adds the **detail** re-run (`buildDetailReRunner`, which threads the production `artistSvc` alongside `searchSvc` into `wireAdmin`): it resolves the top artist through the live search service, then reproduces the mobile client's per-seed artist-detail fan-out (`useArtistContent` — albums deezer/soundcloud/itunes, top-tracks deezer/soundcloud/Last.fm-by-MBID) and its client-side title-merge over the production `GetArtistContentService`, so the operator sees the discography/top-tracks the app actually renders — the gap the search-only re-run can't show, since detail is a separate pipeline (its client-mirror merge is the one part that can't import the TS, so `rerun_detail_test.go` locks the dedupe rules). Admin routing is two-layer: shell/config public, all data routes behind auth + `OperatorOnly` (fails closed when `OperatorUserID` is unset). The public `/health` exposes ok/degraded only — dependency topology is operator-gated, and "not_configured" is deliberately distinct from "down".

**Lifecycle** (`Run`): SIGINT/SIGTERM via `signal.NotifyContext`; shutdown order with individual timeouts — server (30s) → alert monitor → event feed → eval meter → vocab refresh (5–10s each) → acquisition scheduler (30s) → a bounded 30s drain of the shared WaitGroup (`drainBackground`, owned by `Run` since structure-audit F4, 2026-07-16 — a hung ticker can no longer wedge shutdown on the no-audio-store path, which used to bare-`wg.Wait()`) → pool/Redis close last. Background tickers (behavioral refresh 30min, nightly corpus materialize when `BEHAVIORAL_CORPUS_PATH` set, metrics rollup 6h — always on, alert monitor 30s) bind to the Run context and register on the shared WaitGroup.

**cmd/ reuse**: `cmd/api` runs `app.New(...).Run` (subcommands like `migrate-dedup`/`backfill-duration` deliberately bypass app with their own CLI audio-store builder). `cmd/discoveryeval` reuses `BuildSearchService`/`BuildSearchServiceWithTransport`/`BuildVocabularyStore`/`BuildConsensusProviders` — see [eval-harness](discovery/eval-harness.md) — plus `BuildArtistContentService` (`detail_harness.go`, which mirrors `wireDiscoveryContent`'s `artistProviders` map and must be kept in sync with it), the seam its `detail` mode drives: the production artist-content fan-out + MB anchor over a caller-supplied identity store, so the harness can feed deliberately fractured identities and assert the read-time guards clean them (a harness seam only — production still wires the detail service through `wireDiscoveryContent`). `cmd/discoverytrace` reuses the exported `BuildDiscoveryProviders` over its recording transport (its hand-mirror had already drifted — SoundCloud lost the yt-dlp fallback) and ranks through the exported `RankWith`/`Reshape` with the same config flags; it still skips identity-stamping and artwork, and behavioral is nil offline. `buildDiscoveryProviders` (`app.go`) is the one definition both `BuildDiscoveryProviders` and the production search wiring build from — its current roster is Apple Music, Deezer, MusicBrainz (when configured), Last.fm (when configured), SoundCloud (api-v2 with a yt-dlp fallback), YouTube Music, Amazon Music (its internal web-player backend, the same self-hosted-personal-use risk acceptance as SoundCloud's api-v2 client — see `amazonmusic.go`'s AIDEV-DECISION), and Spotify (`spotify.go`, its own anonymous web-visitor bootstrap — a TOTP-gated access token ported from the open-source SpotifyScraper project plus a separate client-integrity token; the most fragile provider in this roster since Spotify actively rotates both the TOTP secrets and the search persisted-query hash, accepted because the other three providers already degrade gracefully around a Spotify outage). Apple Music (`applemusic.go`) replaced plain `ITunesAdapter` in this fan-out (2026-07-22): both hit the identical Apple catalog under the identical ids, but Apple Music's official Catalog API — reached through the anonymous developer token Apple's own web player embeds publicly (`applemusic_token.go`, same risk-acceptance posture) — additionally carries ISRC, composer credits, and a lyrics flag that the plain Search API never exposed, so it strictly supersedes iTunes for fan-out purposes; `ITunesAdapter` itself is untouched and still wired for the artwork chain, album consensus, and content lookups.

**2026-07-24.** `buildDetailEnrichers` no longer constructs the Discogs album/artist enrichment services or their Redis caches; the `HasDiscogs()` branch there is gone. Discogs is still constructed in `search_wiring.go` for album consensus and remains in the artwork chain, so `DISCOGS_TOKEN` is still a live config value — it just no longer gates a detail-enrichment path.

## HTTP client and transport policy

The `clientFactory` factories are the single source of provider HTTP-client policy. Every provider construction used to inline its own `&http.Client{Timeout: ...}` — roughly 30 sites, a couple silently diverged to 15s — so the policy was invisible and easy to copy wrong. Each factory returns a fresh client with its own connection pool.

`providerRateLimits` caps requests per second per provider host on the live path. Exceeding a provider's published limit is what got the IP throttled and surfaced as spurious search timeouts. Unlisted hosts run unbounded (Deezer; SoundCloud carries its own `client_id` throttle). Burst covers one query's per-kind calls — artist + track + album = 3, plus margin — so a single search is not rate-limited against itself, while the sustained rate still paces throughput *across* queries, which is what providers actually throttle on. A nil limiter for an unlisted host is memoized so it is not re-checked per request.

`liveTransport` retries 429 and 5xx with a small linear backoff; other 4xx are the caller's fault and are not retried. A cancelled or expired context ends retrying immediately, since the caller's budget is gone. A body that cannot be rewound (no `GetBody`) is an error, so the caller stops rather than re-sending a consumed body. It serves production and recording only — never replay, where the `Replayer` answers instantly from fixtures. `roundTripper` exists for providers that own their client and accept only a transport (YouTube Music).

## Eval isolation

The eval meter ships off (`EVAL_METER_ENABLED`); when disabled `buildEvalRunner` returns nil and no second provider stack is built at all. When enabled it gets a dedicated search-service instance with its own per-provider circuit breakers, isolated from production's, so an eval failure can never trip a breaker live search depends on. It reuses the pool and Redis, takes a nil event store so synthetic searches do not pollute telemetry, and runs `rankingOnly`: skipping the shared result cache — a cached hit would score the cache rather than the pipeline, masking a regression for the whole TTL — and display enrichment (artwork HTTP that title/subtitle matching never reads), while keeping every rank-affecting flag live. `evalSmokeChecks` is deliberately tiny: a handful of canonical queries per interval cannot meaningfully burn provider quota, unlike the full-corpus offline harness in `cmd/discoveryeval`.

## Operator re-run surfaces

`reRunner` builds providers directly rather than going through `Service`, bypassing the live circuit breakers by construction so a re-run cannot trip a breaker live users depend on. It must rank with the live flag config: passing a zero-value config once made the waterfall silently diverge from production ranking whenever a flag was on, and cross-kind prominence defaults on. `behavioralScores` reads the live `Service`'s published satisfaction snapshot so a re-run applies the same behavioral input production does.

`detailReRunner` covers the gap `/rerun` leaves, since detail is a separate pipeline. It resolves the top artist through the live search `Service`, then fans out the same per-seed content calls `useArtistContent` makes and applies the same client-side merge (dedupe by title, keep highest track-count, newest-first) against the production service instances, so identity resolution, the MusicBrainz anchor and the caches all match the phone.

`BuildArtistContentService` in `detail_harness.go` mirrors `wireDiscoveryContent`'s `artistProviders` map and the two must stay in sync when a content provider is added or removed. It is a harness seam for the `discoveryeval detail` mode, which passes a seeded in-memory identity store to feed deliberately fractured identities; production still wires through `wireDiscovery`.

## Why each provider is wired the way it is

- **TheAudioDB is deliberately not a search provider.** Its free key caps artist search to a single result, which cannot serve the ambiguous-query case, and Deezer/MusicBrainz/Last.fm/YouTube already cover artists. It stays an artwork-by-identity resolver in `buildArtworkChain`.
- **Apple Music replaces iTunes for artist content** — same Apple catalog and ids, but the official Catalog API carries release dates, cover art and ISRC that the plain iTunes lookup misses. iTunes remains a second mainstream source of truth for discography and tracklist, keyed by the `collectionId`/`artistId` its results carry.
- **Apple Music and Spotify serve their own album tracklists natively.** Without them an apple- or spotify-sourced album — the norm on identity-bridged cards, where the Deezer group was dropped by the MusicBrainz anchor — has no supported source and falls back to a blind Deezer title search that returns a different album's tracks. The same was true of SoundCloud-sourced singles before SoundCloud resolved its own tracklists.
- **Last.fm top-tracks is keyed by MBID only**, so it never falls back to ambiguous name matching; the client calls it only for artists with a resolved MBID.
- **Related tracks are track-keyed** — SoundCloud's numeric track id keys `/tracks/{id}/related` — and are SoundCloud-only today.
- The featured-artist resolver tolerates a nil MusicBrainz searcher and degrades to Deezer-only, which is why it must be passed a nil *interface* rather than a typed-nil pointer.
- Identity-first V2 detail is enabled by the durable identity store's presence, wired whenever a pool exists; the shared MusicBrainz adapter supplies the authoritative release-group set V2 checks each fan-out provider against, dropping a mis-bridged same-name artist.
- The recording transport wraps the shared live transport so every provider call on a correlated request lands in the drill-down store. It is bounded and degrades silently.

## Lifecycle

`setup` assembles the graph in dependency order; each `wire*` stage owns one context's construction, and values crossing contexts travel explicitly through the `*Wiring` structs rather than package state. Shutdown drains the shared background group (corpus refresh, metrics rollup) in `app` rather than in the scheduler — without that drain the no-audio-store path leaks goroutines past shutdown — and `drainBackground` gives up after its timeout so a hung background task cannot wedge shutdown.

Health is tri-state: a nil dependency is `not_configured`, intentionally absent and distinct from `down`, so it must not fail readiness. The per-dependency breakdown stays behind the operator-gated `/admin/health` tile.
