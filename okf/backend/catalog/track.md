`Track` (`domain/track.go`) is the catalog context's primary aggregate root, identified by the wrapped-UUID `TrackId` and owned by a `shared.UserId`. It carries title/artist/album plus optional metadata (year, genre, track_number, album_artist, isrc, duration), an ordered `FeaturedArtists []FeaturedArtist` of guest credits (see [featured-artists](featured-artists.md)), and an `AcquisitionStatus` enum (`AcquisitionPending`/`Ready`/`Failed`, zero-value = pending). The status/`AudioRef`/`FailureReason` invariant is enforced only through aggregate methods — `MarkReady(audioRef)` (requires a non-empty ref), `MarkFailed(reason)` (requires a reason, clears the ref), `RevertToPending()` (clears both), `IsStreamable()` (`Ready` AND a non-nil ref) — never by direct field mutation.

`MarkReady` also re-stamps `AudioVersion`, a plain `string` holding a fresh `uuid.NewString()` on every audio write. It exists because `AudioRef` is deliberately *stable*: the acquisition pipeline's object key is derived from `userId/artist/album/title.ext`, so re-acquiring a track overwrites the same object and leaves the ref byte-identical — meaning no field on this aggregate changed when the audio behind it did, and a client caching a copy by track id had no way to tell. `AudioVersion` is that missing content identity, surfaced to clients through `AudioURLService` (see [audio-storage](audio-storage.md)). Empty means no audio has been written under the scheme yet, which callers must read as "no expectation" rather than "mismatch". Why a random token and not a timestamp — a wall-clock stamp only distinguishes writes at the clock's granularity, and the invariant needed is unconditional — is in [tracks-table](../../data/tracks-table.md#audio_version-014-2026-07-31). `NewTrack` validates title/artist (empty either returns `*ValidationError`, part of the catalog-wide `CodedError` vocabulary) and computes a `DedupKey`.

**A single carries its own title as its album.** `resolveAlbum` maps a blank-or-whitespace album to the title, and `NewTrack` applies it before storing either field — so a track saved from a provider that has no album concept (SoundCloud) or that never surfaced one lands as `Crook` / `Raf Saperra` / `Crook` rather than with an empty album. The rule is enforced in the aggregate rather than at the API edge because two things downstream read the album and must agree with each other: `DedupKey` (below) and the acquisition pipeline's object key, which otherwise degrades to a literal `Unknown Album` path segment. The album reaching this aggregate comes from the client's `album` field, which the mobile save path reads solely from a discovery result's `extras["album"]`. Only four providers write that key directly (Deezer, iTunes, SoundCloud, YouTube Music); Apple Music sets `SearchResult.Album` instead, which the search DTO mapper (`search_endpoints.go`) now copies into `extras["album"]` when no provider already claimed it — before that it was dropped on the wire, so Apple-sourced tracks arrived album-less even when Apple knew the answer. `SetAlbum` is the only way to change the album afterwards, and it recomputes `DedupKey` in the same call — the two may never drift, because a row whose stored key disagrees with what `computeDedupKey` would produce silently stops deduplicating and re-saving the track inserts a twin.

`DedupKey` (`domain/dedup.go`) is `lowercase|NFKC-normalized|alphanumeric-stripped` `title|artist|album`, joined with `|`. It backs the persistence adapter's `ON CONFLICT (user_id, dedup_key) DO NOTHING RETURNING id` upsert (`track_repo.go` `Add`), so re-saving the same track by metadata is idempotent: a conflict falls back to `GetByDedupKey` instead of a race-prone read-then-write, and `TrackRepository.Add` returns `(stored, created, err)` so the caller always gets a usable row either way. A fresh insert runs inside the same transaction as the track's featured-artist links, so track and credits commit atomically.

Services (`service/`):
- **`AddTrackService`** (`add_track.go`) validates via `domain.NewTrack`, copies the request's featured credits onto the track before `Add`, and — only when the row was freshly created (`created == true`) — publishes `track_added_to_library` and schedules acquisition via the injected `ports.AcquisitionScheduler` (a one-method port the acquisition context implements; catalog never imports acquisition). The event embeds the *full* wire-shaped track via `trackAddedPayload` so a receiving client can insert the row directly instead of refetching; the payload marshals `service.TrackDTO` — the same struct the handler serializes as `TrackResponse` (`TrackResponse = service.TrackDTO` type alias) — so event and HTTP response cannot drift. The legacy `track_id` key is retained alongside the canonical `id` for older clients. A narrow `trackAdder` interface (just `Add`) is injected rather than the full `ports.TrackRepository`, so the service's dependency surface matches what it actually calls.
- **`DeleteTrackService`** (`delete_track.go`) deletes the row (`trackRepo.Delete` returns `(deleted, audioRef, err)`; a repo-side transaction also strips the track from any playlists and renumbers their positions — see [playlist](playlist.md)) then best-effort deletes the audio file via `ports.AudioStore.Delete`, logging (not failing) on an orphaned file.
- **`SetTrackNumberService`** (`set_track_number.go`) backs persist-as-you-browse: the client derives a track's real album position from the album tracklist and writes it back. Validates `trackNumber > 0` (else `*ValidationError`), then delegates to the repo's fill-only `SetTrackNumber` (`WHERE track_number IS NULL`) — so re-running never clobbers a real value, and `updated == false` (track already numbered, or not found) is a non-error for an idempotent backfill.
- `ListTracksService`/`GetTrackStatusService` are plain reads, not covered further here.

**`track_number` on create was dropped for the whole life of the field (fixed 2026-07-30).** `AddTrackInput` has carried `TrackNumber *int` and `AddTrackService.Execute` has assigned `track.TrackNumber = input.TrackNumber` since the field existed — but the handler's own wire DTO, `CreateTrackRequest` in `track_handler.go`, had no `track_number` field, and `handleCreateTrack` never mapped one into `AddTrackInput`. Go's `encoding/json` ignores unknown fields by default, so the value the mobile client sent on **every** album-context save was decoded into nothing and discarded in silence. The mobile side was doing its part throughout: `toCreateTrackRequest` populates `track_number` from the discovery result's track position, and the TS `CreateTrackRequest` declares it required-and-nullable.

The consequence was the exact outcome the field exists to prevent — a Track saved from an album context reached the database with a null `track_number`, so the library rendered a counted 1..N ordering instead of the real tracklist order. The second path that could have healed it was also cold: `SetTrackNumberService` is implemented, fill-only and unit-tested, and its `PATCH /v1/tracks/{id}/track-number` route is registered, but the mobile `setTrackNumber` client has **zero call sites**, so the persist-as-you-browse backfill this service was written for has never run.

The fix is two lines — the DTO field and its mapping — and it was found by the mobile slice's derived cross-surface contract test rather than by any test on either side individually. That is the point worth keeping: this defect is *invisible* to mutation testing on the client, because the field is sent and ignored, so no client-side mutation changes observable behaviour. Only a test that derives both sides of the wire from source and compares them could see it. Pinned by `TestHandleCreateTrackPersistsTrackNumber` and `TestHandleCreateTrackOmitsTrackNumberWhenAbsent` here, and by the field-set equality assertion in `apps/mobile/src/shared/api-client/__tests__/contract.test.ts`.

Adapter (`adapters/persistence/track_repo.go`): `PgxTrackRepository` shares a `trackColumns`/`trackColumnsPrefixed` canonical 17-column list and a `trackScanDest()` scan/construct helper, reused by playlist-track joins (`playlist_repo.go`) and the featured-artist joins (`featured_artist_repo.go`) so a schema change is a single-line edit. `GetByID`/`ListByIDs` deliberately do **not** load featured credits (every current caller of those two only needs status/audio-ref fields); `ListForUser`/`GetByDedupKey`/`ListTracksFeaturing` do, via a shared batch `loadFeaturedForTracks` (avoids N+1). `ListByIDs` (`WHERE user_id = $1 AND id = ANY($2)`) is the batch read behind audio-URL presigning (see [audio-storage](audio-storage.md)) — unknown/foreign ids are simply absent, order is not guaranteed. `Delete` runs in a transaction: it first finds and clears the track's `playlist_tracks` rows (renumbering each affected playlist via the shared `renumberPlaylistPositions`, see [playlist](playlist.md)), then deletes the track row, returning its `audio_ref` for the service's best-effort file cleanup.

Handler (`adapters/handler/track_handler.go`): `TrackHandler` routes (`GET /`, `POST /`, `GET /{trackId}/status`, `PATCH /{trackId}/track-number`, `DELETE /{trackId}`, plus featured-artist routes mounted via `FeaturedArtistHandler.addRoutes`), all auth-gated via `auth.RequireUserID`. `TrackResponse` is a type alias of `service.TrackDTO` — the wire shape is owned by the service layer for the reason above. Validation lives in the domain (`NewTrack` returns a coded 400); the handler does no duplicated pre-checks and routes every service error through `httputil.HandleServiceError`.

`Track.FeaturedArtists` is empty for tracks whose credits were never resolved, and `TrackRepository.GetByID` / `ListByIDs` deliberately do not load it — their callers read only status and audio-ref fields (the hot one being audio-URL presigning), so the join is not paid on every call.

`trackColumns` and `trackColumnsPrefixed` (the `t.`-aliased form for joins), `playlistTrackCountSubquery`, `renumberPlaylistPositions` and `trackScanDest` each exist so a rule has exactly one definition and cannot drift between the queries sharing it. `renumberPlaylistPositions` in particular is shared by every write path that can drop a `playlist_tracks` row — playlist track removal, and track deletion in `track_repo.go`.

## Failure copy (2026-07-25)

`FailureMessage(reason *string)` maps an acquisition failure reason to the sentence a user reads: `no_match_found` to "Couldn't find this track", `download_failed` to "Download failed", `ytdlp_error` to "Download error", a nil reason to "Acquisition failed", anything unrecognised to "Couldn't get this track". It surfaces as `failure_message` on `TrackDTO`, set only when the track is actually `failed`.

The map lived in the mobile client, which meant the backend could introduce a new failure reason and every already-shipped app would render it as the generic fallback. The reason string stays on the wire too - it is the machine-readable half, and telemetry and the operator console read it.

## Library read models (2026-07-25)

`domain/library_lens.go` sits beside the aggregate but is deliberately not part of it: `AlbumGroup`, `ArtistGroup` and `OwnedTrackRef` are read-side projections over many tracks, with no identity and no invariants. They are here rather than in `service/` so the pgx adapter can return them without importing the application layer.

`LibrarySort` is a three-state enum (`recent` / `az` / `year`) parsed at the edge; an unknown value is a `ValidationError`, never a silent default.

## AcquisitionProvenance (2026-07-26)

`Track` carries a nullable `AcquisitionProvenance *string`, written only through `SetAcquisitionProvenance(AcquisitionProvenance)` — which silently ignores any value outside the three-member vocabulary (`verified`, `corroborated`, `best_effort`), so an unknown string can never reach the column. It records *how strong the claim is* that the stored audio is the recording the user saved: `verified` means an acoustic fingerprint matched the expected MusicBrainz recording, `corroborated` means the audio length agreed with an independently resolved duration, `best_effort` means neither check could run. It is deliberately not part of `MarkReady`'s signature: readiness and confidence are separate facts, and a track acquired before this existed is legitimately `NULL` rather than retroactively downgraded. Set by acquisition's `UpdateTrackStep`; see [acquisition/pipeline](../acquisition/pipeline.md).

## RejectedSourceKeys (2026-07-26)

`Track.RejectedSourceKeys []string` is the accumulating memory of every source a re-acquire has moved away from, written only through `RejectAudioSource` — which ignores an empty key, is idempotent, and trims to the newest 25 so a row cannot grow without bound. `AudioSourceURL` alone was not enough: it names only the *current* source, so the second re-acquire could return exactly what the first one rejected, and because ranking is deterministic it reliably did. Keys are normalized (`youtube:<videoId>` where possible) by acquisition before they arrive, so the aggregate stores opaque strings and never parses a URL — the normalizer is acquisition's, and the direction of that dependency matters: catalog does not know what a YouTube URL is.

## AudioSourceURL (2026-07-26)

`Track.AudioSourceURL *string` records the source URL the stored audio came from, written through `SetAudioSource` (a no-op on an empty string, so a pipeline that somehow produced no candidate cannot blank it). It exists for one reason: acquisition's ranking is deterministic, so re-running it returns the same winner, and a "this is the wrong version" re-acquire needs to *exclude* what it already has. Set by acquisition's `UpdateTrackStep` from the selected candidate. Nullable, and legitimately null for every track acquired before migration 012 — those simply get no exclusion on their first replace.
