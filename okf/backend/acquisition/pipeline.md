Acquisition is a customer of the catalog context: it consumes `catalog/domain.Track` and its `MarkReady`/`MarkFailed`/`RevertToPending` invariants rather than owning its own aggregate. There is no `domain/` folder — `AudioCandidate` lives in `ports/ports.go` and doubles as the pipeline's candidate type (same bounded context, same shape — a service-side twin would only duplicate its fields); the pipeline-scoped types (`TrackRef`, `AcquisitionContext`) live in `service/pipeline.go`.

**Pipeline shape** (`service/pipeline.go`): a `Step` interface (`Name`, `Execute`, `Rollback`) run in order by `RunPipeline`, assembled in exactly one place by `CoreSteps` (shared by the production service and the reacquire CLI, which stops before `UpdateTrackStep`) and pinned by `buildsteps_test.go`, which rolls back completed steps (reverse order, 30s timeout) on failure and wraps the failing step in a `StepError{Step, Err}` — the one structured error shape `failureReason` and the operator console read, rather than parsing an error-message prefix. `AcquireTrackAudioService.buildSteps` (`service/acquire.go`) assembles: `SearchStep` → `SelectStep` → `DownloadStep` → `TagStep` → `StoreStep` → `UpdateTrackStep`. `CoreSteps` (search through store) is factored out separately so the reacquire CLI commands, which update `audio_ref` themselves and stop before the last step, replay the identical sequence instead of a hand-maintained copy that could drift.

- **Search** (`step_search.go`): builds several query variants (ISRC, title+artist, +album, +"audio") and calls `AudioSearcher.Search`, deduping the merged results by URL (`ports.DedupeCandidatesByURL`, shared with the adapter's own engine fan-out below). The yt-dlp adapter (`adapters/ytdlp/searcher.go`) fans each query to two search engines (`ytsearch5:` YouTube, `scsearch5:` SoundCloud — YouTube covers the mainstream catalogue, SoundCloud the unreleased/leaked/underground long tail YouTube doesn't index), merges/dedupes by URL, and only fails if every engine errors.
- **Select** (`step_select.go` + `service/matching.go`): `rankCandidates` scores every candidate with `identityScore` (title/artist fuzzy match via `textnorm.TokenSortRatio`, penalizing title-only matches 0.6x since an unqualified title match is ambiguous — "Die Hard" vs Kendrick's "DIE HARD"), gates out anything below `identityMin` (60), then splits survivors into a Topic-channel bucket (`isTopicChannel`, `- Topic` suffix) and an "other" bucket. Topic candidates sort artist-match first, then feature-match, then identity; other candidates sort by identity, then feature-match (tiebreak), then `metadataRank` (channel/duration/category/view-count blend). Topic-channel candidates always rank ahead of all others — a SoundCloud result only fills a gap when no qualifying YouTube Topic match exists, never displacing a good YouTube one. `extractFeaturedArtists`/`featureMatch` read the *raw* (un-normalized) title because `textnorm.NormalizeForMatch` strips bracketed segments, so by the time `identityScore` compares titles the "(feat. X)" marker is already gone — feature-awareness has to work around that blindness by re-reading the source string.
- **Download** (`step_download.go`): walks the ranked list (capped at `maxVerifyAttempts=4` — each attempt is a full download, so the cap keeps a pathological query from downloading the whole candidate list), downloading each candidate and applying two per-candidate gates before accepting it. Duration gate: when an `AudioProber` is wired and the track has an expected duration, downloads whose probed duration falls outside `durationWithinTolerance` (15s or 7% slack, whichever is larger) are rejected. Decode gate: whenever a prober is wired (independent of expected duration), `ValidateDecodable` must pass — a candidate can carry a valid container and the right duration over corrupt samples that no player can decode (the shipped-m4a defect), so undecodable downloads are discarded and the walk falls through to the next candidate; if every candidate fails, the step errors and the Track is never stored. Both gates fail open when the prober itself errors or times out — verification is skipped rather than blocking acquisition on an unavailable validator. `Rollback` deletes the temp file (`ac.TempPath`, the specific downloaded file, not its containing directory — directory-level cleanup is a separate `CleanupTemp` path in `acquire.go`).
- **Tag** (`step_tag.go` + `adapters/id3/tagger.go`): the step hands the track's metadata to the `AudioTagger` port and swallows (logs) any failure — tagging must never fail the pipeline; without a tagger wired it is a no-op. The id3 adapter writes ID3v2.4 tags (title/artist/album/year/track#/album-artist/genre) via `bogem/id3v2` — but only for `.mp3` files. ID3v2 is an MP3-only convention that prepends a tag block at byte 0; on any other container (e.g. m4a/MP4, which must start with `ftyp` and whose sample-offset table the shift invalidates) that corrupts the file, so the adapter skips non-MP3 files entirely — they carry their metadata in the DB instead.
- **Store** (`step_store.go`): builds a sanitized `userId/artist/album/title.<ext>` audio ref via `BuildAudioRef` — the extension is derived from the downloaded temp file itself (`filepath.Ext`, falling back to `.mp3`), so the ref always names what the download actually produced; hardcoding the format here is how refs lied about their bytes during the m4a era — and calls `AudioWriter.Store`; rollback deletes the orphaned object. When a prober is wired (`buildSteps`/`CoreSteps` always pass `WithStoreProber(s.audioProber)`, a no-op unless `WithAudioProber` was configured), it re-runs `ValidateDecodable` on the final temp file before persisting — the last gate after download and tagging, catching corruption introduced by any earlier step (a format-mismatched tagger, a truncated write) before it reaches the library; unlike the tag step, this failure does fail the pipeline. `sanitizePathComponent` also rejects components that normalize to only dots (a path-traversal token) even though the store defends against escapes independently. `BuildAudioRef` is exported rather than package-private because the ref layout is a contract between this pipeline and anything that has to *find* an already-stored object without having run the pipeline — currently `cmd/backfillaudio` (see [audio-storage](../catalog/audio-storage.md)); a second copy of the sanitizer would drift silently, and the drift would be invisible until a track refused to play.
- **UpdateTrack** (`step_update_track.go`): calls `Track.MarkReady(audioRef)` + `SetDuration` (from the selected candidate's probed duration, when known) and persists; rollback reverts to pending.

**Ports** (`ports/ports.go`): `AudioSearcher` (search+download), `AudioProber` (`ProbeDuration` for true length plus `ValidateDecodable` for playable samples — metadata-only probing can't catch valid-header/corrupt-data files), `AudioTagger` (`Tag(ctx, path, TrackTags)` — implementations decide per-container applicability, so skipping an unsupported container is not an error; implemented by the id3 adapter), `AudioWriter` (store-side subset of catalog's `AudioStore`: `Exists`/`Store`/`Delete`), `TrackRepository` (narrowed `GetByID`/`Update`). The prober adapter (`adapters/ytdlp/prober.go`, `FfprobeProber`) resolves both ffprobe and ffmpeg binaries near yt-dlp's `--ffmpeg-location` dir (falling back to PATH): duration via ffprobe JSON (30s timeout), decodability via `ffmpeg -v error -i file -f null -` (90s timeout) where a non-zero exit means undecodable (error carries the first stderr line, capped at 200 chars). Both probes fail open — if the binary is missing or times out, verification is skipped rather than blocking acquisition on an unavailable validator.

**Events** (`acquire.go`): the service holds an optional `events.Publisher` (`internal/shared/events`, injected via `WithAcquireEvents`; all publishes are nil-guarded for eval/test paths). `Execute` publishes `track_acquisition_started` (`track_id`) before the pipeline runs — the server-authoritative "it's acquiring now" signal the client seeds its download UI from and uses to flip a re-acquired ready/failed Track back to pending, instead of depending on the optimistic save or the poll — then `track_acquisition_completed` (`track_id`, `audio_ref`) or `track_acquisition_failed` (`track_id`, client-safe `reason`). A per-job `track_acquisition_progress` event (`track_id`, `stage`) is published by the scheduler's per-job reporter as each step transitions — see [scheduling](scheduling.md) for that mechanism, since it isn't reachable through the service alone.

`failureReason` (`acquire.go`) maps internal step errors to a small, stable, client-safe vocabulary ("no matching audio found" for search/select, "audio download failed", "audio storage failed", "audio acquisition cancelled" for context cancellation, generic fallback "audio acquisition failed") by matching on the structured `StepError` — `RunPipeline`'s only other error shape is the "pipeline cancelled" prefix — with the full error chain logged, never stored on the track or returned over the wire.

`AcquireTrackAudioService.Execute` re-searches by metadata on every call; there is no direct-download-by-saved-URL path (SoundCloud's public stream for many tracks is only a ~30s preview, which yt-dlp would otherwise store as if it were the full track). `reconcileForReacquire` decides whether a call should even run the pipeline: a `Ready` track whose audio file still exists is a no-op skip; a `Ready` track with a missing file, or a previously `Failed` track, is reverted to pending and re-run; a fresh `Pending` track proceeds unchanged.

## Search and selection

Acquisition always re-searches by metadata. The old direct-download path — fetching a saved SoundCloud permalink verbatim — was removed because SoundCloud's public stream is often only a ~30s preview.

`searchEngines` fans each query to YouTube (the mainstream catalogue) and SoundCloud (the unreleased, leaked and underground long tail YouTube does not index). Selection is Topic-channel-first, so a SoundCloud candidate only fills a gap where no qualifying YouTube Topic match exists and never displaces a good YouTube result. One engine failing is tolerated; the search fails only if every engine fails.

`featuredRe` deliberately excludes "with", which mangles real titles like "Stuck with U" — the same reason `textnorm` dropped it. `extractFeaturedArtists` reads the raw title, because `NormalizeForMatch` strips bracketed segments and by the time `identityScore` compares titles the `(feat. X)` is gone, leaving the matcher blind to features. `featureMatch` then requires a candidate to mention every named featured artist in its raw title; otherwise it is a different recording — the solo cut or official video that the duration-blind identity score cannot tell apart. A track with no feature imposes no requirement. Title-only matches are penalized because without artist context the match is ambiguous ("Die Hard" versus Kendrick's "DIE HARD"), and spaces are stripped when matching channels so spaceless official channels like "TheWeekndVEVO" still match.

Duration tolerance is the larger of an absolute slack and a fraction of the expected length: the same recording from any source runs the same length within a few seconds, allowing for intro/outro or silence trimming, so a larger gap means a different recording.

## Verification and tagging

`ValidateDecodable` exists because `ProbeDuration` is metadata-only: a file with a valid header but corrupt samples passes duration verification and fails here. That is the exact defect that shipped undecodable m4a files. If ffmpeg itself cannot run — missing binary, timeout — validation is skipped rather than blocking acquisition on an unavailable validator, mirroring `ProbeDuration`'s fail-open stance.

ID3v2 is MP3-only. The tagger prepends an ID3 block at byte 0, which is correct for MP3 but corrupts any other container: an m4a/MP4 must start with `ftyp`, and the shifted bytes invalidate its sample-offset table. Non-MP3 files are skipped entirely and carry their metadata in the database.

`reconcileForReacquire` treats a ready track whose audio file still exists as a no-op skip, and reverts a ready track with a missing file — or a previously failed track — to pending. A transient existence-check error falls through to re-acquire rather than skipping, so a possibly-missing file is never left unrepaired.

Acquisition emits a server-authoritative `track_acquisition_started` event so the client seeds its download UI and flips a re-acquired ready or failed track back to pending, instead of depending on the optimistic save or the poll (regression F7/F8).

`CoreSteps` is the single definition of the search -> select -> download -> tag -> store sequence, shared by the production service (via `buildSteps`, which appends its own `UpdateTrackStep`) and the reacquire CLI commands (which update `audio_ref` themselves and stop before that step), so the two callers cannot drift. `CleanupTemp` removes the parent of `TempPath` rather than `TempPath` itself, because `DownloadStep` creates one temp dir per download attempt via `os.MkdirTemp`; it is exported so the reacquire CLI cleans up identically.

## One-off repair commands (`cmd/api/commands`)

Order per track is store the new file, swap `audio_ref`, then delete the old one — never the reverse. If the DB update fails the new file is already stored but the row still points at the old ref, so the track keeps playing and a later run re-processes it, leaving at worst one orphaned file; the old file must not be deleted on that path. A failed or gate-rejected re-acquire leaves the existing file and row untouched, because a broken original is preferable to a lost row. `reacquireTrack` is passed an expected duration (`expectedDuration`: the DB value, else probed from the existing file) so `DownloadStep`'s prober rejects a wrong-length recording.

`truncatedAudioThresholdSecs` (45s) is the line between a truncated preview and a real track: SoundCloud previews are ~30s and the affected tracks all probe at 29.8s, while no track this library cares about is under 45s. Above the threshold the audio is fine and only `duration_seconds` is backfilled with no re-download; below it the track is marked failed and `audio_ref` cleared, so the app offers a retry that re-acquires through the search pipeline.

Historically `backfill_m4a` converted MP3 to native M4A. After the ID3-on-m4a corruption the pipeline was reverted to MP3, so both it and `reacquire_corrupt` now simply re-run tracks through the current pipeline, whose output extension follows whatever that pipeline produces.

## Identity-first acquisition (2026-07-26)

The pipeline no longer identifies a recording by resemblance alone. `AcquireTrackAudioService.resolveIdentity` calls a `RecordingResolver` port — implemented by `adapters/discoverybridge` over discovery's search service — before the steps run, and records the answer on `AcquisitionContext.Identity` (ISRC, MBID, an authoritative duration, and per-provider ids). It is **fill-only and fail-open**: it supplies a duration only when the track carries none, never overwrites saved metadata, and a resolver failure leaves acquisition exactly as it was. That matters because the duration gate was previously conditional on `Track.Duration > 0`, so a track saved without a duration got no length check at all.

Search is now a fan-out over a `SourceRegistry` rather than a single `AudioSearcher`. Every registered `ports.AudioSource` is queried concurrently into its own result slot (so tie order is reproducible run-to-run, never completion order), results merge and dedupe by URL, and the search fails only when *every* source fails — a single source failing is tolerated and logged. A source panicking is recovered into that source's error slot rather than killing the process. `Fetch` routes back to the source that produced the candidate via `AudioCandidate.Source`.

Sources divide into two kinds, and the distinction is a property of the *candidate*, not of the source. A **resolved** candidate (`AudioCandidate.Resolved`) is one whose identity was established upstream: `adapters/ytmusic` reads the YouTube Music video id that discovery already captured, and `adapters/streamrip` builds a Tidal/Deezer/Qobuz/SoundCloud track URL from the same identity. Resolved candidates **skip the identity gate and rank ahead of everything**, because `identityScore` exists to compensate for not knowing what a candidate is — when that is known, the gate is noise. The alternative was fabricating a `- Topic` channel to game the score, which is why the rule against inventing metadata exists. Resolved candidates still pass every *audio* gate; a golden case pins a catalog hit whose audio probes 205s against a corroborated 181s being rejected.

Three verification mechanisms replaced what would otherwise have been a rule per failure mode:

- **Corroborated duration.** When `Identity.Duration > 0` the tolerance tightens from `max(15s, 7%)` to `max(5s, 3%)` (`durationWithinAuthoritativeTolerance`). This is what catches a container carrying the right recording plus foreign audio — a music video with a 12s spoken intro sits comfortably inside the loose window and is obvious against an independently corroborated length.
- **Acoustic fingerprint.** The `AudioIdentifier` port (`adapters/chromaprint`: `fpcalc` → AcoustID → MusicBrainz recording ids) asks whether the downloaded bytes *are* the recording. A mismatch rejects the candidate and the walk continues; an **unknown** result accepts and downgrades provenance, because AcoustID's coverage is crowd-sourced and unreleased material is simply absent — rejecting on unknown would make the long tail unacquirable. Only consulted when `Identity.MBID` is known.
- **Deterministic ranking.** Both sorts are `sort.SliceStable` with an explicit `breakTie` on distance from the expected duration, then URL. Previously two candidates tied on identity, artist-match and feature-match were ordered arbitrarily by `sort.Slice`, so which of a master and a slowed edit entered the library depended on provider response order.

`UpdateTrackStep` now also records provenance via `Track.SetAcquisitionProvenance`, derived from `AcquisitionContext.Provenance()`: `verified` (fingerprint matched), `corroborated` (length agreed with an independent catalogue), or `best_effort` (neither). The result is honestly two-tiered rather than uniformly trusted, and the tier is legible on the track and in the operator console.

Correction to the note above: `SetDuration` is passed `ac.Selected.Duration`, which is the duration the *source reported in its metadata*, not the value `ProbeDuration` measured. The probed number is computed for the gate and discarded, so a stored duration is provider metadata rather than a measurement.

Selection is gated offline by `cmd/acquisitioneval`, which runs the real `CoreSteps` pipeline in-process against committed goldens with case-driven fakes, scores per failure class, and fails against `baselines.json`. It replaced a suite that only proved the ranker was self-consistent against candidates we wrote ourselves — which it still is, since the goldens remain synthetic; recording real provider output is the outstanding upgrade.
