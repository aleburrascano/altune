## SELECTED

- **Table** — `alreadyThereMessage(skipped, playlistName)` is a pure function over two independent branches (`skipped === 1`, `playlistName != null`), giving four rows whose boundary is the exact value `1`. The same `length === 1` boundary is restated in three alert bodies (`mutations.ts:49`, `:98`, `:176`). *Changed from REJECTED* — the first record rejected this as "no branching pure function large enough to enumerate", which is a judgment about size; the *Applies when* column asks only for two or more branches, and applicability is a property of the code. `__tests__/mutations.create.test.tsx`.
- **Derivation** — four gating booleans are computed inside components and reachable only by rendering: `busy = resolving || addMut.isPending || createMut.isPending` (`AddToPlaylistSheet.tsx:55`) gates three controls and an `ActivityIndicator`; `visible && !createVisible` (`:155`) decides which of two modals is on screen; `addedTo === item.id` (`:136`) gates the per-row confirmation; `name.trim().length === 0` (`CreatePlaylistModal.tsx:76`) gates the Create button. Cover the truth table over the derived outputs, not a diagonal through it.
- **Reducer** — the `onMutate` optimistic patches are `(cacheState, variables) → cacheState`: `track_count` bumped on the acting playlist and left alone on every other one (`mutations.ts:77-79`); the detail cache filtered to exactly the surviving tracks (`:165`); the detail name replaced on rename (`:119`). Asserted against seeded non-trivial state — two playlists, three tracks — never an empty cache, because an empty cache cannot distinguish "patched the right one" from "patched everything".
- **Property** — `fast-check` **is** installed (`^4.9.0`; the taxonomy's "no property-based library is installed" note is stale, and `shared/auth` and `shared/api-client` already carry `.property` files). Two laws worth generating: the remove patch is the order-preserving set difference for any track list × any removal set, and every playlist *other* than the target is byte-identical across an add patch for any cache. Both kill index/identity survivors as a class.
- **Invalidation** — `onSettled` must hit `playlistKeys.list` and `playlistKeys.detail(playlistId)` on every membership write, by key identity, because a membership change alters the grid's count and preview artwork as well as the open detail screen. Note the asymmetry to assert deliberately: `useDeletePlaylist` invalidates in `onSuccess`, not `onSettled`, so a failed delete refreshes nothing.

  Authoring this category surfaced a **cross-implementation inconsistency that no test in the repo could have caught**, because the two implementations never call each other. This slice's optimistic patches each touch exactly one cache family — `useAddTracksToPlaylist` bumps `track_count` in `playlistKeys.list` and never the target's own detail; `useRemoveTracksFromPlaylist` and `useRenamePlaylist` patch `playlistKeys.detail` and never the corresponding row in the list. The SSE-side patch for the *same* operations writes both (`shared/events/playlistCachePatch.ts`, lines 15+18 and 33+43), which is what `shared/events`' own rule to keep `track_count` in agreement across the two families requires. So the same user-visible action is consistent when another device performs it and briefly inconsistent when this one does, until `onSettled` refetches. Not data loss, and the refetch bounds it — recorded rather than fixed, because reconciling the two patch implementations is a change to `shared/events` as much as to this slice.
- **Liveness** — `AddToPlaylistSheet` renders `track_count` and `name` straight from the query cache. *This category was silently omitted from the first record*, which is the exact hole the taxonomy exists to prevent, and the mobile `CLAUDE.md` already carries it as a standing rule ("a component that displays server-mutable state gets a liveness test"). Write to `playlistKeys.list` while the sheet is mounted; assert the rendered count changed.
- **Idempotence / replay** — the remove patch must satisfy `apply(apply(e)) === apply(e)`. The add patch deliberately does **not** — it bumps by the requested size at `onMutate` time, so a replay double-counts — and the invalidation of `playlistKeys.list` is what bounds it. Assert the idempotence that holds and assert the correction that bounds the one that does not; do not assert the double-count as an expectation.
- **Adversarial** — the `resolveTrackIds` thunk is a trust boundary the sheet does not own. Three degenerate inputs, each asserting the add endpoint is **never** called: a thunk that rejects (a failed save followed by an add would address an id that does not exist), a thunk that resolves empty (would send `track_ids: []` and take a 400), and a sheet that is not visible. Server side: `added > trackIds.length` and a playlist id absent from the cached list must not produce a message that lies.
- **Failure injection** — six I/O call sites, every one able to fail: `createPlaylist`, `addTracksToPlaylist`, `renamePlaylist`, `deletePlaylist`, `removeTracksFromPlaylist`, `getPlaylists`. Each rejecting path asserts the cache is restored to its exact pre-mutation value. Rollback is the entire reason `onMutate` returns a context; an optimistic update whose failure path is untested is a data-loss bug waiting for a flaky network.
- **Concurrency / ordering** — *changed from REJECTED*. The first record argued the shared `busy` flag makes the row list inert so there is no interleaving to construct. `busy` is React state, so it gates only after a re-render, and two orderings exist regardless of it: `closeTimer.current` (`AddToPlaylistSheet.tsx:80`) is overwritten by a second add, orphaning the first timer past the cleanup effect that only ever clears the current one; and `handleClose` (`:146`) resets `addedTo` without clearing a pending timer, so a manual close leaves a timer that fires `onClose()` again. `CreatePlaylistModal`'s `onSubmitEditing` (`:66`) reaches `handleCreate` without passing the disabled Create button. Each of these is an ordering with a test that fails without the guard, which is the done-condition.
- **Timing / dwell** — *changed from REJECTED*. The first record called the 700ms hold cosmetic and said asserting it would pin an animation constant. It is not an animation: it is the only confirmation the user gets that the add landed, and the taxonomy's own justifying example is a shortened "Done" dwell surviving because the test advanced all timers and asserted the final state. Assert mid-window — the ✓ is still rendered and the sheet still open partway through — then at the boundary.
- **Functional / acceptance** — the two requirements the slice exists to serve, asserted through the sheet in `docs/ubiquitous-language.md` terms with no reference to internals: picking a playlist adds **the resolved ids** so a Track saved on pick reaches the playlist (issue #18), and one gesture over N Tracks produces exactly **one** request (issue #20/#22). The second is `toHaveBeenCalledTimes(1)`, the only assertion that distinguishes a batch client from one that loops.
- **Accessibility** — *changed from REJECTED*. The first record rejected it and then deferred it in the same document, which cannot both be true. The rows carry `accessibilityRole`, an `accessibilityLabel` naming the playlist and its Track count with its own pluralisation branch, and `accessibilityState.disabled` tracking `busy`; both backdrops carry a Close label. The screen-reader *announcement* of the "Added ✓" confirmation stays deferred — there is no `announce` call to assert.

  One result from this category is worth carrying, because it looked like a suite gap and was not. Dropping `accessibilityState={{ disabled: busy }}` from the playlist row survived every mutation attempt, and the reason is in React Native rather than in the tests: `Pressable` computes `disabled != null ? {..._accessibilityState, disabled} : _accessibilityState` (`Pressable.js:228-229`), so a non-null `disabled` prop unconditionally overwrites whatever `accessibilityState.disabled` was passed alongside it. This component always passes `disabled={busy}`, so the explicit attribute is **redundant source** and no RNTL query — including `toBeDisabled()` and `getByRole(..., { disabled })`, which read the same path — can distinguish its presence from its absence. Recorded as genuinely equivalent, and the attribute is listed as dead code rather than deleted.
- **Invariant / architecture** — four `CLAUDE.md` rules in this slice are mechanically checkable: every membership write is a batch (no single-track call path exists in the module's exports), every key is imported from `playlistKeys` and no key literal is retyped, the slice imports no feature, and a failed add inside `useCreatePlaylistWithTracks` is a success with a note rather than a rollback. `shared/lib` and `shared/auth` already carry the `slice-invariants.test.ts` shape to copy.
- **Regression** — the batch rewrite's premise: a Track already in the target playlist is reported as a skipped count, never an error. The singular endpoint answered 409 on a duplicate, so this is the behaviour change the whole slice turns on. Every survivor the mutation audit leaves and every defect authoring surfaces earns a row here too.
- **Mutation audit** — run last, over all four files, by both mechanisms. Until it passes, no claim above is verified. Results and the carried survivors are below.

## MUTATION AUDIT

Two mechanisms, as the programme requires, and they found disjoint things.

**`test-assassin` (semantic, hand-authored).** 59 mutations across the three source files, 54 killed. `mutations.ts` took 23 and lost none — every optimistic-patch identity, rollback path, invalidation key, boundary and field selection is constrained rather than merely executed. The two components took 36 and left 5 survivors, all of which became test fixes except one: dropping `accessibilityState` from the playlist row, which is equivalent for the `Pressable.js` reason recorded under Accessibility above.

**Stryker (generated, reproducible).** Scoped to `src/shared/playlists/**/*.ts`, so `mutations.ts` — the components are `.tsx` and outside the `mutate` glob's shape. **158 mutants, 149 killed, 9 survived — 94.30%**, clearing the standing `break` of 93.

The first Stryker pass scored **91.14%** with 14 survivors, and the 5 it found that the assassin had not are the reason both mechanisms are mandated. Four were `ObjectLiteral → {}` on **request bodies**: `createPlaylist({})`, and the same for the nested create and for `removeTracksFromPlaylist`. A client posting an unnamed playlist, or removing nothing, passed every test — the suite asserted response *handling* exhaustively and never asserted what went over the wire. The fifth was `OptionalChaining` on the skip-count name lookup (`:86`): dropping the `?.` from `getQueryData(playlistKeys.list)?.items` survived, because every skip test had the list cache warm — including the name-lookup-miss test, which seeds a list merely lacking the target id. The genuinely cold case is reachable, since `useAddTracksToPlaylist` is also called straight from `PlaylistDetailScreen`, so a deep link into a playlist detail never populates the grid's list and a skipped add would read `undefined.items`. Source was already correct; the test was the gap. All five now have a test proven red against the mutant by hand.

The 9 remaining survivors are carried as equivalent, in two groups:

- **`context?.previous` guards** (`:93`, `:124`, `:171`, two mutators each = 6). Neither `if (true)` nor dropping the optional chain is observable: `setQueryData(key, undefined)` is a no-op in React Query v5, and `context` is only ever undefined if `onMutate` itself throws.
- **`cancelQueries({ queryKey }) → cancelQueries({})`** (`:72`, `:116`, `:157`). Cancels every query rather than one. Distinguishable only with an unrelated query in flight, which no production path in this slice produces — recorded rather than chased.

**The `.tsx` question this slice was supposed to answer, and why it still stands.** The premise was that a component-bearing slice would show its `StyleSheet`/prop-config mutants swamping its logic mutants. That is not what happened, because the `.ts`-only glob excludes both components before the question arises — the same accident that let the previous seven slices past it. What this run does add is a measured data point on the component side: of 36 hand-authored semantic mutations against the two `.tsx` files, **zero** were presentational noise and 31 were killed, so the components are not intrinsically unmeasurable — they are simply unmeasured by a `.ts` glob. A future slice that wants them in needs a threshold that tolerates the generated presentational mutants, not a better glob.

**The glob was extended, on a measured number.** The combined run over all eight member slices was executed in full *before* the config change — 2,354 mutants, 2,171 killed plus 5 timeouts, 135 survived, 7 uncovered, 36 errored, **93.87%** in 52 minutes. Stryker excludes errored mutants from scoring, so the figure is `2176 / (2176 + 135 + 7)`. That takes the combined score **93.70 → 93.87**, and `thresholds.break` **stays at 93** because 94 does not clear. `src/shared/playlists/**/*.ts` duly joined the `mutate` glob on the same `.ts`-only terms as the seven before it.
