The `tracks` table (defined in `001_baseline.sql`) persists the catalog context's `Track` aggregate root (see [catalog/track](../backend/catalog/track.md)). Columns: `id UUID PK` (default `uuid_generate_v4()`), `user_id UUID NOT NULL` (owning user, no FK — cross-context reference by id per `shared.UserId`), `title`/`artist TEXT NOT NULL`, `album TEXT` (nullable, mapped to Go's `""` when absent), `duration_seconds DOUBLE PRECISION`, `added_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `artwork_url TEXT`, `acquisition_status TEXT NOT NULL DEFAULT 'pending'`, `dedup_key TEXT NOT NULL` with `UNIQUE (user_id, dedup_key)`, plus the extended metadata columns (all present in the baseline itself — there is no later migration adding them): `year`, `genre`, `track_number`, `album_artist`, `isrc`, `audio_ref`, `failure_reason`.

`002_relationship_indexes.sql` adds two case-insensitive indexes for cross-user relationship queries (entity-relationship search enrichment): `idx_tracks_lower_album ON tracks (lower(album)) WHERE album IS NOT NULL AND album != ''` and `idx_tracks_lower_artist ON tracks (lower(artist))`.

The Go domain type (`track.go`) wraps identity in `TrackId` (unexported `uuid.UUID` field) and models `acquisition_status` as the `AcquisitionStatus` enum (`AcquisitionPending`/`Ready`/`Failed`, zero-value `Pending`) via `String()`/`ParseAcquisitionStatus`. `NewTrack` validates title/artist and returns the domain's typed `*ValidationError` instead of a bare `errors.New` error (part of the catalog-wide coded-error vocabulary — see [catalog/track](../backend/catalog/track.md)). It also resolves a blank album to the track's title, so `album` is nullable in the schema but no longer written empty by a fresh insert — the column stays nullable for rows predating the rule, and `idx_tracks_lower_album`'s `album != ''` predicate keeps covering them. Because `dedup_key` is derived from `title|artist|album`, the album and the key must move together: `SetAlbum` is the only writer that changes the album and it recomputes the key in the same call, since a row whose stored key disagrees with what `computeDedupKey` would produce stops matching the `ON CONFLICT (user_id, dedup_key)` upsert below and re-saving that track inserts a twin. The aggregate enforces the `audio_ref ↔ status` invariant through methods (`MarkReady` requires a non-empty `audioRef`; `MarkFailed` requires `reason` and clears `AudioRef`; `RevertToPending` clears both) — never via direct field mutation. `Track` also carries an ordered `FeaturedArtists []domain.FeaturedArtist` of guest ("feat.") credits — not a `tracks` column but two satellite tables (below), loaded and attached by the repository.

`PgxTrackRepository` (`track_repo.go`) implements `ports.TrackRepository`. `Add` runs in a transaction: the insert uses `ON CONFLICT (user_id, dedup_key) DO NOTHING RETURNING id` — a conflict falls back to `GetByDedupKey` so callers get the existing row without a race-prone read-then-write (the deferred rollback disposes the empty tx) — and a fresh insert writes the track's featured-artist links in the same tx so track and credits commit atomically. `SetTrackNumber` is fill-only (`WHERE track_number IS NULL`), so it never clobbers a real value and is idempotent — it backs the client's persist-as-you-browse write-back of album positions for tracks saved before `track_number` was captured, reporting whether a row actually changed. `Delete` returns `(deleted bool, audioRef *string, err error)`: it collects the ids of every playlist the track belongs to, deletes its `playlist_tracks` rows, calls the shared `renumberPlaylistPositions` helper (also used by `playlist_repo.go`'s `RemoveTrack`, see [playlists-table](playlists-table.md)) once per affected playlist so removal never leaves a position gap, then deletes the track itself with `RETURNING audio_ref` so the caller can clean up the underlying audio blob. Column lists are centralized in two string constants, `trackColumns` (bare) and `trackColumnsPrefixed` (`t.`-qualified, for joins in `playlist_repo.go`/`featured_artist_repo.go`), so a schema change is a single-line edit; a shared `trackScanDest()` helper builds the matching scan-destination/`Track`-construction pair. `GetByID` does **not** load `FeaturedArtists` — every current caller only reads status/audio-ref fields, so the join would be paid on every call and discarded; `ListForUser`/`GetByDedupKey`/`ListTracksFeaturing` still attach featured credits via `loadFeaturedForTracks` (one batch query per page, avoiding an N+1), and `ListForUser`'s total count now rides along as `COUNT(*) OVER ()` on the same query instead of a separate round-trip. `ListByIDs` batch-loads a user's tracks by id set (`WHERE user_id = $1 AND id = ANY($2)`) in one query — the batch read behind audio-URL presigning, which resolves up to 200 ids per request. Its contract: unknown or foreign ids are simply absent from the result, order is not guaranteed, and — like the playlist-track joins — it deliberately does not load featured credits.

Featured credits live in two tables (`010_track_featured_artists.sql`, ADR-0019), normalized so "everything featuring X" is an index-clean join (see [catalog/featured-artists](../backend/catalog/featured-artists.md) for the Go-side value object and services). `featured_artists` is the canonical artist — one row per user per identity: `id UUID PK`, `user_id`, optional `mbid TEXT` / `deezer_id BIGINT`, `name`, `norm_name`, and `identity_key TEXT GENERATED ALWAYS AS (COALESCE(mbid, 'dz:' || deezer_id::text, 'name:' || norm_name)) STORED` with `UNIQUE (user_id, identity_key)`. The generated column is deliberately mirrored by the Go value object's `IdentityKey()` (`domain/featured_artist.go`) so Go-side and SQL-side identity agree. `track_featured_artists` is the ordered membership: `PRIMARY KEY (track_id, featured_artist_id)`, `position INTEGER NOT NULL`, both FKs `ON DELETE CASCADE` (so deleting a track needs no manual link cleanup), plus `idx_tfa_featured_artist` for the featuring lookup. Writes go through `featured_artist_repo.go`: `writeTrackFeatured` upserts the canonical artist (`ON CONFLICT (user_id, identity_key) DO UPDATE SET name = EXCLUDED.name`, so display names refresh) and links it `ON CONFLICT DO NOTHING`; `ReplaceFeaturedArtists` verifies track ownership, deletes the track's existing links, and rewrites the set in one transaction — idempotent, used by the featured backfill.

`SetTrackNumber` is fill-only (`WHERE track_number IS NULL`), so it never clobbers a real value and is safe to call repeatedly. On a dedup-key conflict `Add` returns the already-stored track, so the caller needs no second lookup.

## Reads added for the library lenses (2026-07-25)

No column changed. Three read shapes were added over `tracks`:

- **Album groups** - `GROUP BY lower(album) || '|||' || lower(coalesce(album_artist, artist))`, filtered to rows with a non-empty album. Artwork and year come from `(array_agg(col ORDER BY added_at DESC) FILTER (WHERE col IS NOT NULL))[1]` - the most recently added track that has one, matching what the client's fold did when it took the first non-null in `added_at DESC` order.
- **Artist groups** - `GROUP BY lower(artist)`. Note this is `artist`, not `coalesce(album_artist, artist)`: the Artists lens counts performing credits, and using the album artist would fold a guest appearance into the headliner.
- **Ownership refs** - `SELECT id, title, artist, acquisition_status, track_number`, the whole table for one user, no joins. Discovery's ownership stamping reads it per stamped request and matches in Go.

The grouping keys are lowercase-only, deliberately: they reproduce the keys the mobile client used, so no group splits or merges on the way over. They are *not* `dedup_key` - that folds punctuation and would merge albums the user sees as distinct.

Worth knowing if the library grows: the ownership read is unindexed beyond `user_id` and is a full per-user scan. A stored normalized `title|artist` column with an index is the escape hatch, and it needs a backfill whose normalization matches `textnorm.NormalizeForMatch` exactly.

## acquisition_provenance (011, 2026-07-26)

`011_track_acquisition_provenance.sql` adds `acquisition_provenance TEXT` (nullable) plus a partial index `idx_tracks_acquisition_provenance ON tracks (user_id, acquisition_provenance) WHERE acquisition_provenance IS NOT NULL`, so "which of my tracks could not be verified" is an index scan rather than a full per-user pass. Both statements are `IF NOT EXISTS`, and the column is additive-nullable — required, because blue-green runs both versions against one database during the swap, so the outgoing version must tolerate the new schema. The three values and why they exist are documented in [catalog/track](../backend/catalog/track.md); the column is written only by acquisition's `UpdateTrackStep` through the aggregate method, and read into `Track.AcquisitionProvenance` via `trackColumns` / `trackScanDest` like every other field.

## audio_source_url (012, 2026-07-26)

`012_track_audio_source_url.sql` adds `audio_source_url TEXT` (nullable, `IF NOT EXISTS`, no index — it is read only for the row being re-acquired, never filtered on). It stores the URL of the candidate that produced the current audio so the "re-acquire, this is the wrong version" path can exclude it and get the next-best instead; without it a re-acquire would return the identical file, because ranking is deterministic. Written only by acquisition's `UpdateTrackStep` through `Track.SetAudioSource`, and read into `Track.AudioSourceURL` via `trackColumns` / `trackScanDest`. Null for every row predating the migration, which costs nothing beyond a first replace that cannot exclude anything.

## rejected_source_keys (013, 2026-07-26)

`013_track_rejected_sources.sql` adds `rejected_source_keys TEXT[]` (nullable, `IF NOT EXISTS`, no index — read only for the row being re-acquired). It is the memory that makes repeated re-acquisition monotonic: every source a replace has moved away from, held as a normalized key (`youtube:<videoId>`, else a scheme/query-stripped URL) so one recording cannot re-enter under a second URL spelling. Written only through `Track.RejectAudioSource`, which is idempotent and bounded at 25 entries so a row cannot grow without limit. Without it a replace could exclude only the single current source, and because ranking is deterministic the second press returned the file the first press had just moved away from. Why the key is normalized rather than the raw URL: `okf/backend/acquisition/pipeline.md`.
